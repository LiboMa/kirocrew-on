# KiroCrew 的发版节奏与开发方向（2026-10-23）

负责人 2026-10-23：「是否可以拿到 KiroCrew 的开发计划，以及相关 Release 计划，我们的规划可以根据它的发版来设定。」

## 1. 能拿到什么

| 资料 | 在哪 | 能不能拿到 |
|---|---|---|
| 发版记录（版本、日期、正式 / 预发布） | GitHub `kirodotdev/KiroCrew`（公开仓库）的 Releases 与 tags | 能 |
| 每个版本的改动 | 仓库根目录 `CHANGELOG.md`；每个 Release 的说明 | 能。CHANGELOG 会滞后，主干上最新的一节还是 0.9.0 |
| 桌面版的更新通道 | `https://updates.crew.kiro.dev/feed/stable/`（桌面版 `app-update.yml`） | 能 |
| 开发计划 / 路线图 | — | **没有公开的。** 仓库没有里程碑，没有 ROADMAP 文件，规划类标签只有 `P0`。只能从 P0 issue、最近合入的功能 PR 和预发布说明推断，或者直接问 KiroCrew 团队 |

## 2. 发版节奏

- **通道：** nightly、insider（预览）、rc、stable（`release_channel.py`）。
- **正式版：** 0.1.3（08-07）→ 0.2.0（08-09）→ 0.3.0（08-17）→ 0.4.0（08-25）→ 0.4.1（08-28）→ 0.5.0（08-29）→ 0.6.0（09-05）→
  0.7.0（09-15）→ 0.7.1（09-24）→ 0.7.2（09-28）→ 0.8.0（10-09）→ 0.9.0（10-16）。大约一到两周一个小版本。
- **0.10.0：** rc.1 在 10-16 发布，insider.4 在 10-17；正式版还没出。
- **提交量：** 主干每天合入两三百个提交，10-20 以来合入了 71 个标题带 `feat` 的 PR。

## 3. 我们现在用的 KiroCrew

- `deploy/versions.env` 钉的是源码提交 `57df464`（10-11），`KIROCREW_ACCEPTED_VERSION=0.10.0`。
- 它报的版本号是 0.10.0，实际是 0.10.0 正式版之前的主干快照：比 v0.10.0-rc.1 落后 1003 个提交，比现在的主干落后 2189 个提交。
- 升级的护栏已经有了：
  - `tests/kirocrew_contract.json`：平台写的配置键、依赖的报错文字、每个请求体读取的键；
  - 部署时的原生测试：在主机上核对已安装的 KiroCrew，不过就中止部署。
- 升级会重启所有 Gateway。

## 4. 从公开信息看到的开发方向

**成员（mate，原 crewmate）是这两个版本的重点。**

0.9.0 已发布：
- 打开成员时，先汇报它的工作进展；
- 每个成员有一张资料卡，写着权限、模型和日程；
- 每个成员可以有一个看板（预览）；
- 远程 crew 的会话作为「实时窗口」，按机器分组显示（预览）。

主干上还在继续推进：
- 用户可见的「crewmate」改名为「mate」（#20965），我们 owner 边界上那个自动建出来的成员就叫 `mate`；
- 成员可以定时报到（#21172）；
- 模板成员可以提供自己的页面（#22560）。

**新的执行环境。**
- 在 Kiro Cloud Sessions 沙箱里跑聊天（#21260）；
- Coder 远程会话环境（#19833）。

这两项可能影响我们的「跨主机放置」（D49 第 3 期）。

**稳定性与安全。**

0.10.0-rc.1 里有：
- 看门狗能从对话的读取循环之外判断一轮卡住；
- 内部接口的会话身份改用 unix socket 对端凭证核实；
- 一批沙箱与凭证加固。

还开着的 P0 里，有两条和我们直接相关：
- **#11576**：同步的后端健康探测饿死事件循环，导致 Gateway 卡住后崩溃。这正是 2026-10-22 我们在 EC2 上看到的卡顿，它还处在 `needs-investigation`、`needs-info` 状态。
- **#13062**：Gateway 反复崩溃重启之后，丢失约 36 小时内的聊天会话。

## 5. 建议

1. **规划按它的正式版走。** 以后钉 KiroCrew 的正式版 tag，不再钉主干上的任意提交。
2. **跟进方式：** 每出一个正式版，一周内先在临时测试边界上升级，跑契约测试与原生测试，再升级 owner 等边界。
3. **MVP 0.2.0 的第一步是先升到最新的正式版**（0.10.0 发布后就用它）。成员相关的能力在 0.9.0 与 0.10.0 里变化很大，
   `docs/research/2026-10-23-kirocrew-native-capabilities.md` 里待核实的问题，要在要用的版本上回答。
4. **开发计划**没有公开渠道。如果负责人能联系到 KiroCrew 团队，直接要他们的路线图最可靠。
   在此之前，可以每周自动生成一份上游简报：自我们钉的版本以来的发版、P0 的变化、与派发 / 子 Agent / 成员 / Gateway / 看门狗相关的 PR。
5. **把 #11576 和 #13062 记作外部依赖。** 我们在 EC2 上的 Gateway 卡顿记录（崩溃转储、时间点），可以作为 #11576 需要的信息提交给上游。
   提交属于外部操作，须负责人同意。

## 6. 怎么复查

都是公开、只读的查询：

```bash
gh api "repos/kirodotdev/KiroCrew/releases?per_page=20" --jq '.[] | [.tag_name, .published_at[:10], .prerelease] | @tsv'
gh api "repos/kirodotdev/KiroCrew/compare/<我们的提交>...main" --jq .ahead_by
gh api -X GET search/issues -f q="repo:kirodotdev/KiroCrew is:issue is:open label:P0"
```

## 1．0.2.0 要做到什么

| 方面 | 0.1.x | 0.2.0 |
|---|---|---|
| **怎么装** | 我们自己的 EC2，用 `deploy.sh` 部署 | 两种模式，都能一键安装：**单机版**（在自己的 EC2 上运行一行 `install.sh`，也支持 pip / Docker / 源码）和**集群版**（一台控制面主机，加一个 Graviton 主机池） |
| **怎么得到执行环境** | 管理员登记 Worker，Token 要经人手 | 用户在控制台自助「申请 Worker」，可选共享主机或专用主机；后台自动开机、安装、登记；Kiro 由用户自己用设备码登录 |
| **用户的数据放在哪** | 平台主机根卷上的目录 | 每人一块加密的 EBS 卷：工作区、各 Agent 的登录状态、KiroCrew 记忆。换主机就是改挂这块卷，同可用区内用户等待约 15–25 秒（P0 实测） |
| **扩缩** | 固定的几台主机 | 主机池按 CPU、内存、剩余挂载位扩容；尽可能不缩容，不搬用户，只回收空主机 |
| **平台层可用性** | 单台主机 | Litestream 持续备份（RPO ≤ 5 s），另一可用区温备（RTO ≤ 15 min）；可用性目标 99.5%（负责人 2026-10-26 定） |

**不变的**：会话、工作流、Team、共享、接手、公开分享的用法；R10、R7 等安全规则；认证信息不集中存放（随用户的卷走，不用 Secrets Manager）。

## 3．已完成的内容

### P1 打底

| 项 | 做了什么 | 谁会看到 |
|---|---|---|
| 登记规则统一 | 控制台登记、接入码登记都走同一段规则：执行边界在所有 Worker（含已停用、已退役）中唯一；宿主账号在启用的 Worker 中不跨空间复用 | 无（只是更严格） |
| 边界身份与全局 UID | 新边界的 `boundary_id` 与 OS 用户 ID（70000 + 序号，永不复用，避开系统发给普通用户的从属 ID 段）由平台分配，写进边界配置；Worker 的 `/health` 以它为边界标识 | 无 |
| 健康信息补容量 | Worker `/health` 多了内存、CPU、负载、进行中的任务数、子 Agent 上限 | 无（给 P3 的放置用） |
| Engine 租约接口 | 「只有一个 Engine 在跑」抽成接口，现在仍是本机文件锁 | 无 |
| **一次性接入码** | 管理员在「登记 Worker」选「用接入码」，签发只显示一次的码和命令；Worker 主机运行 `octopus worker enroll` 自己登记，Token 不经人手。码只用一次、30 分钟到 24 小时有效、可撤销、失败 5 次作废；部署脚本首次登记也改用接入码。EC2 验收（2026-10-27）：`deploy.sh boundary add` 用接入码登记了一个临时边界，身份、UID、密封、审计都核对通过，验收后已退役 | 管理员 |
| 有副作用的 GET 审计 | 逐条列出全部 GET 路由的副作用。结论：没有一条经登录 Cookie 的 GET 会替用户做主动操作，不必改路由（`docs/research/2026-10-26-get-side-effects-audit.md`） | 无 |
| ARM64 安装 | 安装脚本按 CPU 架构选 Node 与 kiro-cli；部署脚本按机型选 AMI，Graviton 主机可用 | 无 |
| 打包 | 只用标准库构建可复现的 wheel、清单（含这一版测过的组合）与校验和，可选签名；命令 `kirocrew-on`；版本号 0.2.0rc1 | 无（给 P2 的一键安装用） |
| Litestream | 状态栈只留状态桶；Litestream 只装在集群版控制面主机上（不跑 Agent），每秒同步，恢复后用 `backup --source` + `restore-verify` 校验 | 无（给 P5 的温备用） |
| 平台指标 | 每分钟一行 CloudWatch EMF（命名空间 `KiroCrewOn`）：进行中 / 等 Worker / 等配额的会话、失联的 Worker、运行中的演示等；管理员也可读 `GET /v1/admin/metrics` | 管理员（API） |

### P2 单机版一键安装

| 项 | 做了什么 | 谁会看到 |
|---|---|---|
| **一行安装** | `curl -fsSL https://<下载域名>/install.sh \| sudo sh`。先预检，不满足的项一次列全后退出，什么也不改：系统（AL2023、Ubuntu 22.04 / 24.04）、CPU 架构（x86_64 照装，开头结尾各提示一次推荐 ARM64）、root、systemd、磁盘、内存、EC2 实例元数据。`--check` 只做预检 | 安装的人 |
| 按系统的安装步骤 | dnf / apt 两套包名；Python 3.12 用系统的，Ubuntu 22.04 用 uv 管理的 CPython；SELinux 打端口标签，AppArmor 不需要。AL2023 上的命令与原来逐条一致 | 无 |
| **验签安装** | 取频道（`--channel stable \| preview`、`--version`）的发布物：先用内嵌公钥验清单签名（没有签名不装），再核对版本与 wheel 的 sha256；任何一项不符都停在改动之前。pip 渠道：`pip install kirocrew-on` 后 `sudo kirocrew-on setup`，走同一套步骤。发布工具另出频道索引（PEP 503，链接带 `#sha256=`） | 安装的人 |
| **CloudFront 小栈与权限** | 默认建 `kirocrew-on-single`：Elastic IP、只放行 CloudFront 的入站规则、控制台 / 原生 / 预览三个分发、每日快照。源站密钥在主机上生成，不离开主机。缺权限时列出要的权限；装完核对主机角色只剩 Bedrock 调用（与 SSM），否则列出要卸下的策略，「管理 › 部署」一直标红直到卸下。安装用的 AK/SK 只给建栈用。`--no-cloudfront` 时 API 只监听本机，经 SSM 端口转发打开 | 安装的人、管理员 |
| **在控制台登录 Kiro** | 执行环境的主人在「我的设置 › 执行环境」（管理员在「管理 › 执行环境」该行的菜单里）点「登录 Kiro」，对话框给出验证地址与设备码，授权后自动确认。设备码只给主人看，不进审计和日志；同一边界同时只有一个登录 | 每个人 |
| **新建边界** | 单机版的「管理 › 执行环境 › 新建边界」：选属主，几分钟后得到他自己的边界。平台 API 不提权，只留下名称与用户名；root 一侧的服务再校验一遍，只运行 `boundary.sh`；进度、输出与下一步都在页面上，失败的可以再试一次 | 管理员 |
| **部署套件** | `kirocrew-on single native <边界> \| backup --bucket <桶> \| up`，在管理员电脑或 CloudShell 上用管理员凭证运行，主机上不留凭证：给边界开公网原生入口（最多 9 个）、平台数据的异地备份（只能写一个对象、15 分钟内有效的预签名 URL）、更新栈。「管理 › 部署」记下待执行的变更与命令，套件执行完回报 | 管理员 |
| Docker 渠道 | 一个容器、一个边界，用于试用；Agent 不以 root 运行，依赖与主机相同；多架构镜像交给 CI | 试用的人 |

## 4．P0 实测的主要结论

详见 `docs/research/2026-10-26-p0-results.md`。

- **同可用区搬一块卷**：200 次 0 失败，用户等待 p50 16.7 秒、p95 19.3 秒、最长 26 秒。
- **挂卷上限**：m8g.large 一台能挂 31 块数据卷，m7g.large 只有 26 块。
- **30 块卷同时搬**：40 秒内全部完成，没有被 API 限流。
- **挂载中被强行卸离**：数据不坏，另一台主机上 0.15 秒内能重新挂好；但主机代理必须先卸载再卸离。
- **跨可用区**：从快照恢复时，默认的懒加载首读只有 8 MiB/s，5 GiB 要 11 分钟；设预置初始化速率后 50 秒读完。跨可用区迁移因此必须带这个参数。
- **重复 UUID**：一律按卷的序列号挂载，从快照复制的卷先换 UUID。
- **停机再开**：停机到重新可用（SSM 上线）约 1 分钟；休眠省不了时间，SSM 要 5 分钟才重新上线。

## 6．升级须知（预览版 0.2.0rc1）

- **版本号**：平台与 Worker 上报 `0.2.0rc1`，控制台包版本为 `0.2.0-rc.1`。
- **数据库**：
  - 启动时自动从 15 迁移到 19：新增表 `boundaries`、`worker_enrollments`、`aws_requests`，`tokens` 多一列 `kind`；迁移前自动备份（`octopus-v15-<时间>.sqlite3`）。
  - 回退到 0.1.x 时，旧版本遇到 19 会拒绝启动：用这份备份恢复，再启动旧版本。
- **新的管理员接口**：
  - `POST` / `GET /v1/workers/enrollments`、`DELETE /v1/workers/enrollments/<id>`；
  - `POST /v1/admin/boundaries`；
  - `GET /v1/admin/metrics`；
  - `GET` / `POST /v1/admin/boundaries/provision`（新建边界，单机版）；
  - `GET` / `POST /v1/admin/aws-requests`、`POST /v1/admin/aws-requests/<id>/done`（部署套件的待执行项）。
- **新的用户接口**：`POST` / `GET /v1/workers/<id>/kiro-sign-in`（在控制台登录 Kiro，只给该执行环境的主人）。
- **新的命令**：`kirocrew-on setup`（pip 渠道）、`kirocrew-on single …`（部署套件）；主机上有 `/usr/local/bin/kirocrew-on`。
- **新的公开接口**：`POST /v1/workers/enroll`，不需登录，凭接入码。
- **Worker 的登记方式**：
  - `deploy.sh boundary add` 与 `worker-host register` 的首次登记改用一次性接入码，`worker-host register` 不再经 SSM 读取 Token；
  - 已登记过的边界或主机，重跑时仍用 `bootstrap-worker` 更新连接。
- **新边界的系统账号**：UID = GID = 70000 + 序号（由平台分配，永不复用），以系统账号创建，不分从属 ID。已有边界保持原来的 UID。
- **平台指标**：API 每分钟向 `/var/log/kirocrew-on/metrics.emf.log` 追加一行（10 MB 轮转一代），需要时由 CloudWatch Agent 收走。
- **Litestream**：只装在不跑边界的集群版控制面主机上（`deploy/install/litestream.sh`）。现有主机不装，也不需要任何新权限。
- **发布物**：`tools/build_release.py` 生成 wheel、清单与校验和，可选签名；本期只产出、不上传。
- **用户看得见的变化**：
  - 管理员的「登记 Worker」多了「用接入码」；
  - 会话与任务的状态：已完成为绿、进行中为蓝（负责人 2026-10-27）；有问题为红或黄；
  - 「我的设置 › 执行环境」多了「登录 Kiro」（管理员在「管理 › 执行环境」该行的菜单里），Kiro 登录过期的提示改为由执行环境的主人在这里登录；
  - 单机版上管理员多了「新建边界」与「管理 › 部署」。
- **部署后要重新登录一次控制台**：Token 从这一版起记下签发方式。新建账号、重设密码、设为管理员、恢复已停用的账号只认控制台登录，Coding Agent 与 API Token 做不了。此前的登录没有这个记录，一律按 API Token 算。
- **域名不变**：控制台、预览、将来的原生入口都在 `tinyboat.blog` 下，隔离做法见设计 §8.2a。

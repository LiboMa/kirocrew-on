在 KiroCrew 聊天里直接对话，也能回到平台续作（D73）：技术架构、实现与验证报告

2026-10-23。已部署 EC2 3af7331，在 owner 边界的会话 run-588bc3d5 上端到端验证。设计稿：docs/superpowers/specs/2026-10-23-chat-and-structured-iteration-design.md；续作的原理：docs/CONTINUE.md。HTML 版：docs/reports/2026-10-23-d73-chat-collaboration.html。

1. 结论

  • 能用。
    • 用户在 KiroCrew 原生聊天里直接和父会话的 Agent 对话：问进展、让它改代码、让它派子 Agent、让它总结，都做到了。
    • 回到平台续作时，聊天里的 3 处改动被完整提交成新的候选，审查、返工、Evaluator 都在它之上照常进行，没有一处改动丢失。
  • 改动很小。 核心是父会话 Agent 的提示：由「只解释」改为「会话协作者」。另有两处配合：
    • 平台开始执行时在聊天里写一行；
    • 续作前提交聊天里的改动。

    合计约 200 行代码，不新增对外接口，KiroCrew 不改。

  • 验证中发现 3 个问题。 两个已在提示里修正，待随下次部署生效；一个是用法上要注意的点： > 聊天里改了行为，续作时要同步改需求，否则审查会按原需求把改动改回去。

2. 技术架构

角色是谁做什么
用户你在原生聊天里直接对话；需要结构化迭代时，回控制台续作
父会话 AgentKiroCrew 的 poc-coordinator，会话的父会话 octopus-run-<id>回答问题；会话停下时按要求改工作区、派 poc-kiro / poc-claude / poc-codex 子 Agent；帮用户总结
平台 EngineKiroCrew ON唯一按任务表派发的一方：每个任务一次尝试，照常把关、纠错、记录
Worker每个执行边界一个建父会话、派子 Agent、写聊天里的说明、提交候选、跑检查命令
工作区与会话分支<worker>/run-<id>/workspace/project，分支 octopus/<run>两种方式共用的状态：候选提交加未提交的改动

写者规则：同一时间只有一个写者。

  • 平台在运行时，写者是平台；
  • 会话停下后，写者是对话。

聊天里的 Agent 靠两行说明判断现在谁是写者：「KiroCrew ON 开始执行：…（Attempt X）」和「KiroCrew ON 执行 Attempt X 已返回」。这一点只靠提示约束。

状态衔接：

  • 平台 → 对话：聊天里已有完整的历史（建立说明，以及每个任务的开始与结果说明），Agent 从中查找，不需要额外接口。
  • 对话 → 平台：续作时，平台先把工作区里不在候选中的改动提交为新的候选，再继续。

3. 实现细节

3.1 改了什么

文件改动
octopus/prompts.py COORDINATOR父会话 Agent 的系统提示（Gateway 模板），改为「会话协作者」：
· 以聊天里的说明、交接、工作区为准回答；
· 平台不在执行时可以改工作区或派子 Agent（只从三个工具里选，cwd 为工作区，keep: true）；
· 平台在执行时不动手；
· 不推送、不建 PR、不改 .octopus/、不读凭证；
· 总结时与需求原文对比
octopus/worker.py OBSERVER_CONTEXT每个新父会话建立时写入的背景，内容同上，只对新会话生效
octopus/worker.py _start_note派发成功后，往父会话写「KiroCrew ON 开始执行：<任务>（<工具>，Attempt X）」。用 KiroCrew 的 note：可见、不触发模型。同一个 Attempt 只写一次（start-note.json），写不成不影响派发
octopus/worker.py 说明文字建立说明与结果说明的前缀，由「Octopus」统一为「KiroCrew ON」
octopus/chat_changes.py（新）collect：续作事务之前，先检查、再提交对话中的改动。apply：在续作事务里记录这次尝试并重置之后的任务。refuse：工作区有未提交的对话改动时，拒绝「请求诊断」
octopus/domain.py Service.operate续作前调用 collect；续作事务里调用 apply；请求诊断前调用 refuse；修订摘要前加「对话中的改动：N 个文件」
web/src/lib/labels.ts事件 run.chat_changes 的中文名称「提交了对话中的改动」

3.2 续作前提交对话中的改动

  1. 预检：与续作自己的检查相同：
    • 版本号、会话已停下且打开、执行环境为这个空间服务；
    • D49 边界主人、Team 未归档、不是工作流建议会话。

    任何一项不过就不调用 Worker，交给续作报错。这样，续作不允许的人不会让对话中的改动先被提交。

  2. 取会话分支上最新的候选，再用 Worker /candidate，mode: check 对比。干净且 HEAD 就是候选时，什么都不做。
  3. 用 Worker /candidate，mode: commit、parent 为最新候选，把工作区现状提交为新的候选，包括 Agent 自己做的提交。有疑似凭证或 .env 时分支不动，续作返回 409 chat_secret 并列出文件。
  4. 记为最后一个写代码任务上的一次「对话中的改动」尝试：
    • 门禁：native_completed 为 skip、diff_present 为 pass、no_secrets 为 pass；
    • 这个任务这次不重跑、又有检查命令时，先跑检查命令（Engine 照现有逻辑轮询）；
    • 它之后、仍标为已交接的任务，一律重置；
    • 事件 run.chat_changes；修订摘要以「对话中的改动：N 个文件」开头。

为什么必须由平台先提交：

  • 审查结束时，平台会把工作区「放回」到候选（sources.rewind）：未提交的改动和候选之后的提交都会被撤掉，所以 Agent 在聊天里自己 git commit 也保不住；
  • 下一个若是实现任务，聊天里的改动又会被算成它的改动。

3.3 错误码

码什么时候
409 chat_secret续作时，对话中的改动里有疑似凭证或 .env（分支不动）
409 chat_changes工作区有未提交的对话改动时请求诊断（请改用续作）

5. 发现的问题与处理

#问题原因处理
1Agent 把平台已提交的工作说成「没入库」提示只说了「续作时平台会先提交工作区里的改动」，它理解成所有工作都没提交已改提示：平台每个任务结束时改动已提交为候选，只有聊天里的改动要等续作。待随下次部署生效
2聊天改了行为，总结却说「需求没变」；续作后审查按原需求把改动改回去Agent 看不到会话的需求原文，用「用户的要求做完了」代替了「需求有没有变」已改提示：需求以最近一次尝试的 instructions.md 开头为准（路径写在提示里）；改变了行为或范围时写「需求有变化」，并给出续作时应填的完整新需求
3总结里编了一句用户没说过的话模型补全已改提示：「事实以文件与命令输出为准，不替用户补充他没说过的话」
4续作对话框没有提醒「工作区里有对话中的改动」设计里没有待负责人决定：在续作对话框里显示「工作区里有对话中的改动（N 个文件）；如果改了行为，请同步修改本次完整需求」。这只是提示，不拦截

第 2 项是这次最重要的用法要点，已写进 docs/CONTINUE.md §5 与常见问题：聊天里改了行为，续作时要把「本次完整需求」改成新的需求。

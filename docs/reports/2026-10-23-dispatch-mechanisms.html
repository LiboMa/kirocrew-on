KiroCrew ON 的派发机制，与本机 KiroCrew、原版 PoC 的比较

2026-10-23。EC2 上运行 a183d84，KiroCrew 0.10.0；本机为 KiroCrew 桌面版 0.8.0（Gateway 127.0.0.1:5476）。

三者用的是同一套 KiroCrew 子 Agent，差别在于由谁决定下一步。KiroCrew ON 由平台代码按任务表决定，并对每一步把关；本机 KiroCrew 由聊天里的模型决定；原版 PoC 由 KiroCrew 里的协调者模型按一段固定流程的提示决定，用一个脚本做检查。

报告后半部分回答两个问题：a183d84 之后父会话为什么不再逐个任务回复，以及用户能否在聊天里继续和各个子 Agent 对话。后者现在不支持，第 6 节是补上它的设计，等你确认后再实现。

1. 谁决定下一步

KiroCrew ON平台 Engine（代码）决定
  1. Kiro 规划一次
  2. 平台按任务表派 task-1
  3. 子 Agent 执行
  4. 平台把关：交接、改动、秘密、检查命令
  5. 失败：自动重试或诊断返工
  6. 派下一个任务
  7. 追加 Evaluator，完成、发布
本机 KiroCrew 0.8.0聊天里的模型决定
  1. 你在聊天里说
  2. 模型决定派不派、派谁、派几个
  3. 子 Agent 执行（可并行）
  4. 结果回到对话，模型读后决定下一步
  5. 模型自己判断是否完成
原版 PoC 流水线协调者模型按提示决定，脚本检查
  1. 协调者按提示派 plan（Kiro）
  2. checkpoint 脚本校验
  3. 派 code（Claude Code）
  4. checkpoint
  5. 派 review（Codex）
  6. checkpoint
  7. 派 deliver（OpenCode）
实底 平台代码 虚线 模型判断 灰底 确定性脚本 白底 子 Agent 干活

3. 三条链路的细节

KiroCrew ON

  1. 控制台、CLI 或 MCP 提交，平台登记 Request 与会话。
  2. 选执行环境：先选你自己的边界，再看 Team；并发上限满了就排队。
  3. Worker 准备工作目录，建立父会话 octopus-run-<id>（Agent 为 Owner 观察员）。
  4. Engine 每秒一轮，取会话里第一个未完成的任务。
  5. Worker 写本轮 instructions.md（角色卡片、需求、契约、前序交接摘要、技能、结尾要求），调用 POST /api/spawn，再调用 mark-collected。
  6. 查看进度：运行 2 分钟内每 2 秒，之后 5、10、20 秒；Gateway 推迟时每 20 秒。
  7. 结束后按证据把关，记下提示与失败；失败进入纠错。
  8. 全部完成后追加 Evaluator（与作者不同的工具）和 Knowledge，然后完成；需要时自动发布 Draft PR。

本机 KiroCrew 0.8.0

  1. 你在桌面版的聊天里提需求。
  2. 聊天 Agent 自己判断：简单的自己做，两个以上独立任务才派子 Agent。
  3. spawn_run：后台派出、立即返回；子 Agent 结束时，结果以「完成事件」注入对话，触发一轮。
  4. spawn_sub_agents：并行派出、等全部结束、收齐结果再继续；同时标记已收取，不再注入。
  5. 还可以 spawn_continue、spawn_steer、spawn_release、spawn_list、spawn_status。
  6. Conductor：与目标、流水线、台账、安全 Conductor 对话即可启动，它们驱动其他会话。
  7. 限制：并发上限自动（最多 32）；空闲内存低于 4 GB 时推迟；子 Agent 最长 3 小时、1000 轮。

原版 PoC 流水线

  1. pipeline.py 建立聊天，Agent 为 poc-pipeline-coordinator，把需求发进去。
  2. 协调者按提示用 spawn_run 派 plan，指定 Agent、阶段标记、cwd、keep=true。
  3. 派完结束本轮，等完成消息。
  4. 收到后调用 pipeline.py checkpoint（不用模型：归属、后端、文件、diff、测试、哈希）。
  5. 退出码为 0 才进入下一阶段；不过就续接同一个工作者补齐，最多两次。
  6. 审查发现缺陷：把审查结论交回原编码会话修复，再让原审查会话复审，最多两轮。
  7. 最后写 report.md，把各阶段任务 ID 与验收结果交回父会话。

4. 差异与取舍

可预测，换来的是灵活性。平台按任务表推进，同一个需求每次的路径一样，每一步都有记录和检查；代价是一个会话里任务只能一个一个跑，不能像本机那样让模型临时并行派出好几个。

把关放在平台，不放在提示里。原版 PoC 已经有确定性检查，但要靠协调者记得去调用；现在由 Engine 在每次尝试结束后强制执行，模型跳不过去。

纠错有边界。自动重试、看门狗、诊断返工都有预算（默认纠错 2 轮、自动重试 4 次、720 分钟），用完就停下说明原因，不会无限循环；本机和 PoC 都没有这层兜底。

原生能力用得少。平台没有用 KiroCrew 的 Conductor、动态工作流、成员和并行波次（见第 7 节）。这是刻意的：平台只认自己派出、能核实归属的子 Agent。要用这些能力，需要先想清楚平台怎样记录和把关它们。

5. a183d84 之后，父会话为什么不再逐个任务回复

KiroCrew 的默认行为是：子 Agent 结束时，_subagent_done 把一条「子 Agent 完成」注入它的父会话；父会话空闲就立即跑一轮（起一个 kiro 进程、消耗 Kiro credits，由观察员写一段回复），忙就排队，一批的最后一个还会再排一轮汇总。派发时的 silent: true 只关 Slack 和 Dashboard 的通知，不影响这一轮。

平台从 GET /api/spawn/{id} 自己读结果，不需要这一轮。KiroCrew 自己的 spawn_sub_agents 遇到同样的问题，用的办法是 mark-collected：把子 Agent 的 ID 记进父会话内存里的「已收取」集合；结束时 KiroCrew 在注入前、等待后各查一次，在集合里就记为已交付、直接返回，不注入、不跑这一轮，也取消汇总轮。a183d84 让 Worker 每次派发、续接、模型探测之后立刻这样标记。

父会话里的内容之前之后
平台的建立说明有有
每个尝试结束时平台写的结果说明（任务结果摘要，最长 3800 字）有有
KiroCrew 注入的「子 Agent 完成」有无
观察员读完结果写的回复（一轮模型）每个任务一段无
一批结束后的汇总回复可能有无

所以聊天里仍能逐个看到每个任务的结果。结果说明走 POST /api/chat/slots/{slot}/note：记录里写一行可见的说明，同时成为下一轮的背景，但不触发模型。你接着提问时，观察员能看到这些说明并回答。

EC2 核对（run-d62631d5）：父会话 4 行记录，其中 2 条结果说明，0 段模型回复；Gateway 日志 2 次「skipping injection」。部署前同样两个任务的 run-656be0a4 跑了 2 轮。限制：「已收取」只存在 Gateway 内存里，任务运行中 Gateway 重启，它结束时照旧跑一轮。

现在支持到哪一步

想做的事KiroCrew 原生平台现在

能绕过去吗：在原生页面用 /agent 把父会话换成会派发的 Agent，它可以续接平台的子 Agent。但平台完全看不到：没有尝试记录、不跑检查与审查、不进时间线与用量；它改过的文件会被下一个平台任务的候选提交带走，还可能让下一个任务报出不是它造成的提示。不建议。

补上的机制：对话续接

原则：平台仍是唯一的派发者，聊天只是入口。每一次和子 Agent 的交互，都是这个任务的一次尝试，照常检查、记录、计入预算，在控制台看得到；子 Agent 带着它上一轮的上下文继续；不加任何确认或等待。

聊天入口如何认定是谁发的

原生登录覆盖整个 Gateway（K03），消息本身不带身份。平台只读「8 小时内有人为它打开过原生入口」的会话，并把最近 8 小时内为这个会话打开原生入口的人当作发送者，按控制台同样的权限检查（能续作的人；个人边界上只有边界的主人；Team 未归档；执行环境仍为这个空间服务）。

这段时间里如果还有别人打开过同一执行环境的原生入口，平台无法确定是谁发的：不执行，在聊天里说明请到控制台操作。宁可不执行，也不冒用身份。

成本

只对 8 小时内打开过原生入口的会话，每 5 秒读一次最近 20 条消息；不新增模型轮次：续接本身就是你要的那一轮，观察员对你消息的回复是 KiroCrew 原有的行为。之后的任务会重新执行，与自动返工相同。

7. 平台还没用到的 KiroCrew 能力

能力是什么可能的用处
并行波次（batch_id）一次派出多个子 Agent，结束时汇总同一会话里并行跑互不依赖的任务，例如几个只读审查同时进行
Conductor目标、流水线、台账、安全四种，驱动其他会话长周期目标；要先解决平台怎样核实它派出的会话
动态工作流（/api/workflows/run）KiroCrew 自己的工作流，带预算与超时与平台工作流的关系待定
成员与小组（/api/members、/api/teams）固定成员和常驻线程，按成员委派把任务交给某个常驻成员
会话分叉、旁路问答、导出导入fork、side、export / import从一个会话分出一份自由探索的副本；只读地问问题
补充说明的 follow_up 模式本轮结束后再接着跑一轮平台目前只用 interrupt，因为另起的一轮平台看不到

8. 需要你确认

  1. 第 6 节的对话续接按这个设计做吗？四个入口；续接这个任务原来的子 Agent 对话；照常把关；做不了就当场说明原因。
  2. 续接之后，之后的任务重新执行？我的建议是重跑，因为它们基于旧的输出。代价是多跑几个任务。
  3. 聊天发送者的认定规则？无法确定是谁时不执行，改用控制台。代价是多人共用一个执行环境时聊天入口不可用。
  4. 运行中的 Claude Code / Codex 任务：直接说明，还是排队等它结束再续接？我的建议是直接说明，因为排队等于新增一种等待。
  5. 部署 5fd7976 与 2c3206e？即响应压缩与写入时打码，回归全部通过；只重启 API 与 Worker。

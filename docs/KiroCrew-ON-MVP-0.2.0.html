1．0.2.0 要做到什么

方面0.1.x0.2.0
怎么装我们自己的 EC2，用 deploy.sh 部署两种模式，都能一键安装：单机版（在自己的 EC2 上运行一行 install.sh，也支持 pip / Docker / 源码）和集群版（一台控制面主机，加一个 Graviton 主机池）
怎么得到执行环境管理员登记 Worker，Token 要经人手用户在控制台自助「申请 Worker」，可选共享主机或专用主机；后台自动开机、安装、登记；Kiro 由用户自己用设备码登录
用户的数据放在哪平台主机根卷上的目录每人一块加密的 EBS 卷：工作区、各 Agent 的登录状态、KiroCrew 记忆。换主机就是改挂这块卷，同可用区内用户等待约 15–25 秒（P0 实测）
扩缩固定的几台主机主机池按 CPU、内存、剩余挂载位扩容；尽可能不缩容，不搬用户，只回收空主机
平台层可用性单台主机Litestream 持续备份（RPO ≤ 5 s），另一可用区温备（RTO ≤ 15 min）；可用性目标 99.5%（负责人 2026-10-26 定）

不变的：会话、工作流、Team、共享、接手、公开分享的用法；R10、R7 等安全规则；认证信息不集中存放（随用户的卷走，不用 Secrets Manager）。

项做了什么谁会看到

Litestream状态栈只留状态桶；Litestream 只装在集群版控制面主机上（不跑 Agent），每秒同步，恢复后用 backup --source + restore-verify 校验无（给 P5 的温备用）

4．P0 实测的主要结论

详见 docs/research/2026-10-26-p0-results.md。

  • 同可用区搬一块卷：200 次 0 失败，用户等待 p50 16.7 秒、p95 19.3 秒、最长 26 秒。
  • 挂卷上限：m8g.large 一台能挂 31 块数据卷，m7g.large 只有 26 块。
  • 30 块卷同时搬：40 秒内全部完成，没有被 API 限流。
  • 挂载中被强行卸离：数据不坏，另一台主机上 0.15 秒内能重新挂好；但主机代理必须先卸载再卸离。
  • 跨可用区：从快照恢复时，默认的懒加载首读只有 8 MiB/s，5 GiB 要 11 分钟；设预置初始化速率后 50 秒读完。跨可用区迁移因此必须带这个参数。
  • 重复 UUID：一律按卷的序列号挂载，从快照复制的卷先换 UUID。
  • 停机再开：停机到重新可用（SSM 上线）约 1 分钟；休眠省不了时间，SSM 要 5 分钟才重新上线。

5．0.1.1 之后已上线（EC2 已部署，随 0.2.0 发布）

功能说明
接手共享来的会话（D74）协作者或 Team 成员能把同一个会话（提交历史不变）接手到自己的执行环境，此后以自己的身份、凭证和用量续作；创建者可以接回。MCP octopus_takeover；接手后用量按人拆开

原生入口的登录在 1 小时后结束（K03 过渡修复）KiroCrew Gateway 原先另发 30 天的刷新凭据，现在被拦下；原生页面不再自己刷新登录，到期时提示重新登录

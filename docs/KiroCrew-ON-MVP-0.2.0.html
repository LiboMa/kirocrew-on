1．0.2.0 要做到什么

方面0.1.x0.2.0
怎么装我们自己的 EC2，用 deploy.sh 部署两种模式，都能一键安装：单机版（在自己的 EC2 上运行一行 install.sh，也支持 pip / Docker / 源码）和集群版（一台控制面主机，加一个 Graviton 主机池）
怎么得到执行环境管理员登记 Worker，Token 要经人手用户在控制台自助「申请 Worker」，可选共享主机或专用主机；后台自动开机、安装、登记；Kiro 由用户自己用设备码登录
用户的数据放在哪平台主机根卷上的目录每人一块加密的 EBS 卷：工作区、各 Agent 的登录状态、KiroCrew 记忆。换主机就是改挂这块卷，同可用区内用户等待约 15–25 秒（P0 实测）
扩缩固定的几台主机主机池按 CPU、内存、剩余挂载位扩容；尽可能不缩容，不搬用户，只回收空主机
平台层可用性单台主机Litestream 持续备份（RPO ≤ 5 s），另一可用区温备（RTO ≤ 15 min）；可用性目标 99.5%（负责人 2026-10-26 定）

不变的：会话、工作流、Team、共享、接手、公开分享的用法；R10、R7 等安全规则；认证信息不集中存放（随用户的卷走，不用 Secrets Manager）。

3．P1 打底已完成的内容

项做了什么谁会看到
登记规则统一控制台登记、接入码登记都走同一段规则：执行边界在所有 Worker（含已停用、已退役）中唯一；宿主账号在启用的 Worker 中不跨空间复用无（只是更严格）
边界身份与全局 UID新边界的 boundary_id 与 OS 用户 ID（70000 + 序号，永不复用，避开系统发给普通用户的从属 ID 段）由平台分配，写进边界配置；Worker 的 /health 以它为边界标识无
健康信息补容量Worker /health 多了内存、CPU、负载、进行中的任务数、子 Agent 上限无（给 P3 的放置用）
Engine 租约接口「只有一个 Engine 在跑」抽成接口，现在仍是本机文件锁无
一次性接入码管理员在「登记 Worker」选「用接入码」，签发只显示一次的码和命令；Worker 主机运行 octopus worker enroll 自己登记，Token 不经人手。码只用一次、30 分钟到 24 小时有效、可撤销、失败 5 次作废；部署脚本首次登记也改用接入码。EC2 验收（2026-10-27）：deploy.sh boundary add 用接入码登记了一个临时边界，身份、UID、密封、审计都核对通过，验收后已退役管理员
有副作用的 GET 审计逐条列出全部 GET 路由的副作用。结论：没有一条经登录 Cookie 的 GET 会替用户做主动操作，不必改路由（docs/research/2026-10-26-get-side-effects-audit.md）无
ARM64 安装安装脚本按 CPU 架构选 Node 与 kiro-cli；部署脚本按机型选 AMI，Graviton 主机可用无
打包只用标准库构建可复现的 wheel、清单（含这一版测过的组合）与校验和，可选签名；命令 kirocrew-on；版本号 0.2.0rc1无（给 P2 的一键安装用）
Litestream状态栈只留状态桶；Litestream 只装在集群版控制面主机上（不跑 Agent），每秒同步，恢复后用 backup --source + restore-verify 校验无（给 P5 的温备用）
平台指标每分钟一行 CloudWatch EMF（命名空间 KiroCrewOn）：进行中 / 等 Worker / 等配额的会话、失联的 Worker、运行中的演示等；管理员也可读 GET /v1/admin/metrics管理员（API）

4．P0 实测的主要结论

详见 docs/research/2026-10-26-p0-results.md。

  • 同可用区搬一块卷：200 次 0 失败，用户等待 p50 16.7 秒、p95 19.3 秒、最长 26 秒。
  • 挂卷上限：m8g.large 一台能挂 31 块数据卷，m7g.large 只有 26 块。
  • 30 块卷同时搬：40 秒内全部完成，没有被 API 限流。
  • 挂载中被强行卸离：数据不坏，另一台主机上 0.15 秒内能重新挂好；但主机代理必须先卸载再卸离。
  • 跨可用区：从快照恢复时，默认的懒加载首读只有 8 MiB/s，5 GiB 要 11 分钟；设预置初始化速率后 50 秒读完。跨可用区迁移因此必须带这个参数。
  • 重复 UUID：一律按卷的序列号挂载，从快照复制的卷先换 UUID。
  • 停机再开：停机到重新可用（SSM 上线）约 1 分钟；休眠省不了时间，SSM 要 5 分钟才重新上线。

5．0.1.1 之后已上线（EC2 已部署，随 0.2.0 发布）

功能说明
接手共享来的会话（D74）协作者或 Team 成员能把同一个会话（提交历史不变）接手到自己的执行环境，此后以自己的身份、凭证和用量续作；创建者可以接回。MCP octopus_takeover；接手后用量按人拆开
公开分享（D75）「预览产出」旁的下拉菜单 ›「公开分享…」：把会话的页面或运行中的演示发给没有账号的人。可选四位授权码或无需授权码，有效期 1 天 / 7 天 / 30 天 / 永久。链接放在会话自己的预览域名上（<run>.preview.tinyboat.blog）；授权码有防爆破；页面分享不提供源码与配置
原生入口的登录在 1 小时后结束（K03 过渡修复）KiroCrew Gateway 原先另发 30 天的刷新凭据，现在被拦下；原生页面不再自己刷新登录，到期时提示重新登录
本地 / 远端联动补齐（D58）同步先鉴权，再读请求体；只读 Token 也能拉回；没有新提交的同步被拒；octopus login 先收窄 Token 文件的权限再写入

6．升级须知（预览版 0.2.0rc1）

  • 版本号：平台与 Worker 上报 0.2.0rc1，控制台包版本为 0.2.0-rc.1。
  • 数据库：
    • 启动时自动从 15 迁移到 17，新增表 boundaries 与 worker_enrollments；迁移前自动备份（octopus-v15-<时间>.sqlite3）。
    • 回退到 0.1.x 时，旧版本遇到 17 会拒绝启动：用这份备份恢复，再启动旧版本。
  • 新的管理员接口：
    • POST / GET /v1/workers/enrollments、DELETE /v1/workers/enrollments/<id>；
    • POST /v1/admin/boundaries；
    • GET /v1/admin/metrics。
  • 新的公开接口：POST /v1/workers/enroll，不需登录，凭接入码。
  • Worker 的登记方式：
    • deploy.sh boundary add 与 worker-host register 的首次登记改用一次性接入码，worker-host register 不再经 SSM 读取 Token；
    • 已登记过的边界或主机，重跑时仍用 bootstrap-worker 更新连接。
  • 新边界的系统账号：UID = GID = 70000 + 序号（由平台分配，永不复用），以系统账号创建，不分从属 ID。已有边界保持原来的 UID。
  • 平台指标：API 每分钟向 /var/log/kirocrew-on/metrics.emf.log 追加一行（10 MB 轮转一代），需要时由 CloudWatch Agent 收走。
  • Litestream：只装在不跑边界的集群版控制面主机上（deploy/install/litestream.sh）。现有主机不装，也不需要任何新权限。
  • 发布物：tools/build_release.py 生成 wheel、清单与校验和，可选签名；本期只产出、不上传。
  • 用户看得见的变化：
    • 管理员的「登记 Worker」多了「用接入码」；
    • 状态配色改为完成为蓝、运行中为绿、有问题为红或黄（负责人 2026-10-26）。
  • 部署后要重新登录一次控制台：Token 从这一版起记下签发方式。新建账号、重设密码、设为管理员、恢复已停用的账号只认控制台登录，Coding Agent 与 API Token 做不了。此前的登录没有这个记录，一律按 API Token 算。
  • 域名不变：控制台、预览、将来的原生入口都在 tinyboat.blog 下，隔离做法见设计 §8.2a。

8．已知问题与后续

  • P1b：KiroCrew 升到正式版 v0.10.0 会改变原生页面的体验，等负责人确认（见第 9 节）。
  • P0b：T5、T6、T11、T13 要在 arm64 上装好 KiroCrew ON 后做；T5 需负责人用设备码登录。
  • 接入码的次要项：失败计数可被绕开、Worker URL 的回环与重定向、签发人失效后码仍有效、控制台列表不自动刷新等，记在 BACKLOG。
  • 同一域名下的残余风险：Agent 做的演示页可以把 tinyboat.blog 的 Cookie 写满，让这个浏览器暂时打不开（读不到、也改不了任何人的数据）。清除该域名的站点数据即可恢复（OPERATIONS「会话独立预览域名」）。

9．需要负责人决定的

负责人 2026-10-27 已定：不另购域名。原生入口与预览都沿用 tinyboat.blog，同站带来的问题由设计在源站一级解决（设计 §8.2a）：

  • Cookie 一律 __Host-；
  • 凭 Cookie 的写入与子资源请求按来源拒绝；
  • 原生入口的中转只放行它自己的登录 Cookie。

剩下的一点是：Agent 做的演示页可以把这个域名的 Cookie 写满，让该浏览器暂时打不开，清除站点数据即可恢复，读不到也改不了任何人的数据。

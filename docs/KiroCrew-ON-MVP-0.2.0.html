1．0.2.0 要做到什么

方面0.1.x0.2.0
怎么装我们自己的 EC2，用 deploy.sh 部署两种模式，都能一键安装：单机版（在自己的 EC2 上运行一行 install.sh，也支持 pip / Docker / 源码）和集群版（一台控制面主机，加一个 Graviton 主机池）
怎么得到执行环境管理员登记 Worker，Token 要经人手用户在控制台自助「申请 Worker」，可选共享主机或专用主机；后台自动开机、安装、登记；Kiro 由用户自己用设备码登录
用户的数据放在哪平台主机根卷上的目录每人一块加密的 EBS 卷：工作区、各 Agent 的登录状态、KiroCrew 记忆。换主机就是改挂这块卷，同可用区内用户可见约 20–60 秒
扩缩固定的几台主机主机池按 CPU、内存、剩余挂载位扩容；尽可能不缩容，不搬用户，只回收空主机
平台层可用性单台主机Litestream 持续备份（RPO ≤ 5 s），另一可用区温备（RTO ≤ 15 min，可用性目标待负责人定）

不变的：会话、工作流、Team、共享、接手、公开分享的用法；R10、R7 等安全规则；认证信息不集中存放（随用户的卷走，不用 Secrets Manager）。

2．分期与进度

期内容状态
P0 实测在一次性测试资源上测 13 项：卸挂时延、挂卷上限、登录能否随卷走、共享主机的内存互扰等；费用 ≤ $20待负责人批准资源，并配合设备码登录
P1 打底新边界由平台分配身份与全局 UID；修好两处登记不一致；人工接入改用一次性接入码；Engine 租约接口；健康信息补容量；打包（wheel + 签名清单）；安装脚本支持 ARM64；Litestream；平台指标；KiroCrew 升到正式版；有副作用的 GET 审计实施中（用户体验不变）
P2 单机版一键安装install.sh 支持四种系统 / 架构组合，加 pip、Docker；控制台里的 Kiro 设备码待 P1
P3 集群版底座主机代理、用户卷、Host 路由的原生入口、迁移编排；只开放给管理员待 P0 实测，以及负责人选定独立域名
P4 自助申请与切换普通用户申请共享 / 专用主机，双向切换待 P3
P5 迁移现有部署与温备personal 退役，现有边界搬到用户卷，温备与演练待 P4

3．0.1.1 之后已上线（EC2 已部署，随 0.2.0 发布）

功能说明
接手共享来的会话（D74）协作者或 Team 成员能把同一个会话（提交历史不变）接手到自己的执行环境，此后以自己的身份、凭证和用量续作；创建者可以接回。MCP octopus_takeover；接手后用量按人拆开
公开分享（D75）「预览产出」旁的下拉菜单 ›「公开分享…」：把会话的页面或运行中的演示发给没有账号的人。可选四位授权码或无需授权码，有效期 1 天 / 7 天 / 30 天 / 永久。链接放在独立的预览域名上；授权码有防爆破；页面分享不提供源码与配置
原生入口的登录在 1 小时后结束（K03 过渡修复）KiroCrew Gateway 原先另发 30 天的刷新凭据，现在被拦下；原生页面不再自己刷新登录，到期时提示重新登录
本地 / 远端联动补齐（D58）同步先鉴权，再读请求体；只读 Token 也能拉回；没有新提交的同步被拒；octopus login 先收窄 Token 文件的权限再写入

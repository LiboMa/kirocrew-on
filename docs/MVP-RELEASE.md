# MVP Release 计划与状态

更新日期：2026-10-10　·　当前阶段：**设计中**　·　本仓库代码：**无**　·　已发布版本：**无**

本文记录 KiroCrew ON 首个可用 MVP 的范围、已确定决策、各里程碑交付与验收条件。
“已确定”“默认值（待确认）”“未开始 / 待验收”分别标注；不要把本文中的目标当作已上线功能。

## 1．MVP 定义

**首个可用 MVP = M1（运行底座）+ M2（核心日常闭环）在 EC2 上完成验收。**
M3（共享与组织）、M4（仓库闭环）在 MVP 之后分别立项，各自经过 spec → plan → 实施 → 验收。

状态标记：`未开始` · `设计中` · `实现中` · `待验收` · `已验收`（附证据位置）· `未通过`（附原因与恢复条件）

| 里程碑 | 状态 |
|---|---|
| M1 运行底座 | 设计中 |
| M2 核心日常闭环 | 未开始 |
| M3 共享与组织 | 未开始 |
| M4 仓库闭环 | 未开始 |

## 2．已确定决策

以下决策已由项目负责人在 2026-10-10 的设计讨论中确认。

| ID | 决策 |
|---|---|
| D01 | 在 `kirocrew-on/` 新建仓库，以新版 `octopus/` 为主干，迁入旧版成熟资产；原目录与运行数据不动 |
| D02 | 交付一份覆盖全部阶段的总体 Design；详细实施计划先只写 M1，后续里程碑在前一阶段验收后再分别出 spec 与 plan |
| D03 | M1 的 Linux 开发与验收直接在 EC2 上进行（实例创建需单独授权） |
| D04 | EC2 使用 Amazon Linux 2023 x86_64 |
| D05 | 实施路线：先等价迁入并建立回归基线，再在测试保护下分步重构 |
| D06 | 核心功能：Session 可共享给个人 / Team / 公司；Skills 对接后端提交任务；后端自动分析、拆分并映射 Agent（可在 Prompt 中指定）；通过报告与 Branch 跟踪 Feature；可用代码实现的功能不依赖 Agent 的通用性；后端接收、记录、分析处理并监控请求 |
| D07 | M2 在审查通过后**只推送远端 Feature 分支**；Draft PR / MR 创建放到 M4 |

## 3．设计默认值（已提出，待确认）

以下是设计中采用的默认值，尚未得到明确确认；如有异议，修改后同步更新本表和 README。

| ID | 默认值 | 理由 |
|---|---|---|
| P01 | Python 包名保持 `octopus` | 兼容 `python -m octopus`、`/v1` API 与 13 个 `octopus_*` MCP 工具 |
| P02 | 旧版 Workflow Studio（8917）不迁入，继续在原目录作为旧版入口 | 新版已有对应的业务服务；旧版独有功能在功能对照表中逐项标注补齐里程碑 |
| P03 | 新应用使用独立数据根，不改动现有 `octopus.sqlite3` | 保留历史数据；如需导入旧数据另做显式迁移工具 |
| P04 | 前端继续使用无构建的原生 JS | 复用现有 UI，不以重写前端为默认方案 |
| P05 | 平台（API / Engine）与执行（Worker / Gateway）分属不同 OS 用户 | 平台身份与执行身份从第一天起分离，为 M3 的隔离升级打基础 |
| P06 | M1 远程访问使用 SSM 端口转发，不开放公网端口 | 符合“初期管理隧道”；团队阶段再上 HTTPS 反向代理 |
| P07 | 一个部署对应一个组织；“共享给公司”= 组织内全部在册用户 | 首个云端实现为单公司部署，多公司 SaaS 不在范围内 |
| P08 | Session 共享角色：`viewer`（查看状态、报告、事件、diff）与 `collaborator`（可续作、提交修订；执行仍使用 Session 所属执行边界的身份与凭据） | 共享 Session 不等于共享凭据 |
| P09 | 共享 Session 不开放原生 KiroCrew 入口 | 当前原生浏览器登录覆盖整个 Gateway，不是单 Session 票据，平台撤权也不会使其失效 |
| P10 | 提交后自动拆分与映射；默认在 Coding 工具中展示计划，由用户确认后运行；个人 / Team 可为指定仓库开启“自动准入”策略跳过确认，并留存策略快照 | 同时满足“自动”与“直接运行必须显式配置” |
| P11 | Feature 报告使用固定章节模板，可按 Team / Workflow 指定；由代码从结构化证据生成，Agent 只写叙述摘要并标注来源 | 代码优先原则 |
| P12 | 首批 Skill 支持 Claude Code 与 Kiro CLI，底层统一调用确定性的 `octopus` CLI；stdio MCP 作为备用通道 | 用户不必自己配置 MCP |

## 4．MVP 范围

### 包含

- 新旧两版资产的等价迁入、来源记录与回归基线。
- 可配置运行时、无桌面启动、systemd 服务、schema 迁移、EC2 单执行边界部署。
- Request（需求请求）一等对象：登记、幂等、状态、与 Session / Run 的关联。
- 自动分析拆分（Kiro）+ 代码执行的 Agent 映射策略 + Prompt 中的显式指定。
- 确认模式与显式配置的自动准入模式。
- Claude Code / Kiro CLI Skill 与 `octopus` CLI。
- Feature 分支、确定性测试门禁、独立审查、诊断返工与复审。
- 请求监控：心跳、超时、卡住检测，阻塞原因与可执行操作。
- Feature 报告（模板化），Web 与 Coding 工具均可查询。
- 审查通过后推送远端 Feature 分支。

### 不包含（MVP 之后）

- Session 共享给个人 / Team / 公司与组织层（M3）。
- 真实独立的 Team 执行隔离、排队与配额（M3）。
- Draft PR / MR 创建、Webhook / Issue 输入、远端检查状态同步（M4）。
- 自动合并、生产发布（独立策略，不是自动研发的隐含默认）。
- 远程 HTTP MCP transport、SSO、高可用、任意 DAG / 并行分支、长期 Team Memory。

## 5．M1 运行底座

### 交付

1. **迁入与基线**：按原相对路径原样迁入，`PROVENANCE.md` 逐文件记录来源路径、sha256 与来源处 git 状态；现有回归测试与 UI 检查在新仓库原样通过。
2. **接手材料**：新旧功能对照表（已复用 / 部分实现 / 缺失 / 计划淘汰及替代）、当前事实清单、主要调用链、已知故障清单。
3. **运行时配置**：解释器、KiroCrew 安装、工具路径、端口、数据根、HOME、公开 URL、日志目录统一配置；保留 macOS 路径兼容。
4. **依赖解耦**：平台侧代码不再依赖 Worker 侧模块（`domain.py → workflow_workspace`、`intent.py → 旧 ui/`）。
5. **组合启动**：`composition` 包加载 `PocProviderRegistry` 等现有组合逻辑，提供 `--check`；普通 Gateway 启动不代表已获得多后端路由。
6. **无桌面启动与服务生命周期**：独立的 API、Worker、Gateway 服务入口；systemd unit、就绪检查、优雅重启、日志、重启恢复；不依赖 Electron 或浏览器。
7. **持久数据**：代码目录、平台数据、Worker 数据、原生 Crew 数据分离；schema 版本迁移，升级不初始化已有数据库。
8. **凭据与环境**：各工具在执行用户下初始化认证；平台只保存必要引用；Worker Token 不以明文存放。
9. **网络入口**：明确内部端口与用户入口；Host 白名单；验证 Host / Origin / Cookie、SSE、原生跳转和隧道路径。
10. **版本与回滚**：固定 KiroCrew、Coding 工具、ACP 适配器和 Node / Python 版本；记录迁移与回退步骤。
11. **备份恢复**：在独立目录实际恢复平台数据库、源码与必要原生数据，列明未覆盖内容。
12. **运维手册**：首次启动、升级、重启、日志、端口、认证过期、停止失败、磁盘与队列异常。

### 验收条件

- [ ] 新仓库内回归测试与 UI 检查全部通过（记录实际运行的命令与输出）。
- [ ] EC2（AL2023 x86_64）上 KiroCrew Gateway 以组合方式无桌面启动，`--check` 证明各后端路由正确。
- [ ] Kiro、Claude Code、Codex 的真实最小研发与返工在 EC2 上跑通，证据包含实际后端、原生 ID、源码基线、diff 与测试结果。
- [ ] OpenCode 单独核实；失败如实记录，并提供用户可见的替换配置。
- [ ] API / Worker / Gateway 重启后状态可恢复，原生执行身份与持久化记录一致。
- [ ] 备份在独立目录恢复成功，源数据保留。

## 6．M2 核心日常闭环

### 交付

1. **Request**：需求请求的数据表与 API，字段包括提交者、个人 / Team、来源（Skill / Web / API）、目标、仓库与 ref、指定的 Agent 映射、执行策略、时间戳、关联 Session / Run；先定义表与 API，再补迁移与权限测试。
2. **分析与拆分**：Kiro 后台设计任务产出任务列表、各任务提示词、验收条件与角色类型；结果由代码校验。
3. **映射策略**：代码按“任务角色 → 工具 / 模型 / Effort”策略表映射，Prompt 中的显式指定优先；按 Worker 实际公布能力校验，记录每项映射来源。
4. **准入**：确认模式（默认）与按仓库范围显式授权的自动准入模式，留存策略快照。
5. **Skill 与 CLI**：Claude Code / Kiro CLI Skill；`octopus` CLI 自动识别 cwd 仓库信息，支持提交、查看计划、确认、查询状态与报告、续作。
6. **Feature 分支**：每个 Feature 一个平台创建的分支，命名规则由代码保证唯一；续作沿用原分支与 Workspace。
7. **确定性门禁**：编码任务结束后由 Worker 运行仓库声明的测试 / 构建命令并记录真实退出码与输出，再交给审查 Agent。
8. **监控**：心跳、超时与卡住检测；阻塞时说明当前 Task、原因类别、已发生 / 未发生的事、可执行操作和证据入口。
9. **Feature 报告**：模板化报告，汇总需求、任务、映射、diff 摘要、门禁结果、审查结论、纠错记录、分支与推送状态。
10. **远端分支推送**，规则如下：
    - 推送由 Worker 代码执行，不由 Agent 执行。
    - 只推送绑定已通过门禁与审查的候选 commit；交付后又修改代码必须重新验证。
    - 写凭据按仓库授权，属于执行边界；不写入 Workspace，不进入 Agent 上下文。
    - 只推送平台创建的 Feature 分支；不推送默认分支，不 force push。
    - 推送回执丢失先查询远端 ref 再决定是否重试；远端分支或基线变化时显示冲突，不覆盖。

### 验收条件

- [ ] 在 Claude Code 中通过 Skill 用自然语言提交需求，后端登记 Request 并返回计划。
- [ ] Prompt 中指定的映射（如“用 Codex 审查”）被采用并在记录中标注来源；不可用的指定给出原因，不静默替换。
- [ ] 确认后在 EC2 上对一个获授权的已有小型仓库完成：clone → Feature 分支 → 编码 → 门禁 → 独立审查 → 故障返工 → 复审。
- [ ] 审查通过后远端出现对应 Feature 分支，commit 与已验证候选一致。
- [ ] Web 与 Coding 工具查询同一 Session，看到一致的状态与报告。
- [ ] 卡住或超时被检测并展示具体原因；缺源码、认证或输入时等待而不是无限重试。
- [ ] 推送回执丢失、远端分支已变化两种情况不产生重复或覆盖。

## 7．MVP 验收矩阵

| 场景 | 必须观察到的结果 |
|---|---|
| Skill 提交自然语言需求 | Request 被登记；仓库 remote / 分支 / HEAD 由代码识别；重复提交返回原回执 |
| 自动拆分与映射 | 任务、提示词、验收条件与 Agent 映射可见；映射来源可追溯 |
| Prompt 指定 Agent | 指定优先于策略；能力不支持时明确拒绝并说明 |
| 使用已有代码库 | 实际源码就绪后才派发编码，记录 ref / SHA / cwd |
| Claude 编码、Codex 审查 | 路由证据与原生 ID 对应正确工具，审查使用真实候选与门禁结果 |
| 审查要求修改 | Coordinator 诊断，原 Workspace 返工，下游重新复审 |
| 模型受限或不匹配 | 请求值与实际值分开，给出原因，不静默成功 |
| 缺源码或认证 | 明确等待原因，可恢复，不无限重试 |
| 原 Session 续作 | Session / 父会话 / Workspace / Feature 分支保留，新增修订与 Attempt |
| 派发响应丢失 | 保留未知状态并核实，不重复启动编码 |
| 服务或浏览器重启 | 状态可恢复，原生执行身份与持久化记录一致 |
| 远端分支推送 | 只推送已验证候选；回执丢失不重复，远端变化显示冲突 |
| 备份恢复 | 在独立环境恢复成功，源数据与旧 Session 保留 |

## 8．继承的已知问题

以下问题来自现有项目文档（`kirocrew-octopus/docs/MVP-1.0.0-RELEASE.md`、`MVP-1.0.0-STARTUP.md`、

属于历史报告记录，迁入后需要复现与处理。

| # | 问题 | 影响的里程碑 |
|---|---|---|
| K01 | OpenCode 执行曾返回空结果，交付未通过 | M1 |
| K02 | 含 `/`、`:`、`[]` 的模型 ID 被原生 spawn 格式拒绝（影响 OpenCode `provider/model` 与部分 Codex 模型 ID） | M1 |
| K03 | 原生浏览器登录覆盖整个 Gateway，不是单 Session 票据；平台撤权不会使其失效 | M1 / M3 |
| K04 | 新版 Web 未代理原生权限批准；存在待批准项时停止可能挂起 | M2 |
| K05 | Kiro 不报告实际模型；模型目录依赖 ACP 缓存，公布的模型不代表有配额 | M1 |
| K06 | 父会话 note 上限约 4000 字符，Worker 截断到 3800；截断不能当作完整交接 | M2 |
| K07 | 原生 continue 不读取 `reasoning_effort`；原生 spawn 没有 HTTP 幂等键 | M1 |
| K08 | Coordinator “不派生任务”的限制来自提示词，不是工具级隔离；其诊断可能有误 | M2 |
| K09 | Engine 单线程串行推进，慢 Run 会阻塞其他 Run | M2 |
| K10 | SQLite 没有 schema 迁移机制；Worker Token 以明文存放 | M1 |
| K11 | 组合逻辑只存在于单个进程内；任何 re-exec 都会丢失 `PocProviderRegistry` | M1 |
| K12 | Linux 沙箱依赖非特权 user namespace；不经官方 launcher 启动时需单独核实（AL2023 未实测） | M1 |
| K13 | 现有启动器与路径依赖 macOS：`/Applications/...`、App 内置 Python、zsh、Electron、`lsof`、Homebrew 路径 | M1 |
| K14 | 旧版 Host 校验固定为 `127.0.0.1:<port>`，隧道或反向代理下会失败 | M1 |

## 9．历史验证基线（来源记录，非本仓库复跑）

据 `kirocrew-octopus/docs/MVP-1.0.0-RELEASE.md` 记录，新版最近一次 Coordinator 功能验证包含：

- 66 项后端回归通过：42 项 Team / Worker、8 项原生入口、16 项纠错。
- 85 项浏览器检查通过；其中模拟响应与真实原生实验分开记录。
- 6 项本机原生接入契约检查通过，用于 KiroCrew 0.8.0 兼容核对。
- 一个真实受控故障实验：Claude 编码 → Codex 测试拒绝 → Kiro 决定返工 → Claude 修复 → Codex 独立复测，最终两项测试通过。
- 更早的四阶段实验实际调用过 OpenCode，但 OpenCode 交付未通过。

这些结果均在 macOS 本机获得。小型实验不代表大型仓库、Team 隔离、EC2 或所有模型组合已通过。
迁入后的第一项工作是在本仓库重新运行回归，并以实际输出替换这里的引用。

## 10．验证分层与证据规则

- 分层记录：单元 / 集成替身、浏览器、原生契约、真实 ACP、Linux / EC2、Team 隔离、Connector；各层不得互相替代。
- 每项验收记录：环境、版本、测试方法、真实结果、证据位置和未通过项。
- 真实 ACP 实验使用单独明确的测试项目，不在用户历史 Session 上做删除或故障注入。
- 原始证据留在部署环境，不提交公开仓库；仓库只提交脱敏摘要。
- 未完成的关键目标保留为未通过项，不合并成“全部通过”。

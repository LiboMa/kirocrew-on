# 用户需求与重要设计决定

整理日期：2026-10-09。来源：本次 Codex 对话中用户的明确要求及已接受的选择。
这是产品需求记录；不把探索问题自动转成已验证能力。

## 产品主线

用户希望以 KiroCrew 为终端，自行选择 ACP Coding 后端，配置各任务的模型与 Effort，
通过 Chat、配置文件、Web 前端构建工作流，并实时跟踪开发。
客户演示要使用 KiroCrew 已有接口；用户无需自行编写 Agent 接口或手工维护 Plan.md / Tasks。

## 已识别的限制

1. 首版是顺序工作流，1–8 个任务；不宣称支持任意 DAG、分支条件或并行调度。
2. 一个 KiroCrew 主对话协调多个子 Session；工具原生 Session 不是共享的同一个上下文窗口。
3. 子任务通过文件交接。本 PoC 使用 `include_memory=false`，不依赖长期 Memory。
4. Claude 具体候选来自本机 ACP 缓存；缓存不是全局模型目录或账号权限保证。
5. Codex Model / Effort 参数已有真实运行证据，完整动态模型目录与逐模型 Effort 列表仍待补全。
6. Session 归档只作用于工作台列表；另有显式关闭 / 重新打开 / 删除操作，详见 SESSION-OPERATIONS.md。
7. 自动生成只输出工作流草稿，不自动批准权限或运行生成结果。
8. Release 文档描述已观察到的交接与验证状态，不替代实际发布或安全验收。

## 学习诉求保留

用户希望通过《Learn KiroCrew the Hard Way》了解架构、模块、交互逻辑与开发流程，
目标是成为贡献者。偏好费曼式、逐步解释，不出题；按需要深入具体代码。

已提出的学习议题包括：

- Memory V1 / V2、召回链、Embedding 与 Chunk 的来源和关系。
- Alternative ACP Harness、Provider 认证与第三方服务集成。
- 主 / 子 Session 的上下文、记忆、持久化和复用边界。
- 原生 Session、KiroCrew Session、Coding Tool 之间的身份区别。
- ACP Token 用量是否可观察、如何证明模型与 Effort 实际生效。

这些议题保留为教程线索；本文不以未核验的记忆推断替代源码解释。

## 2026-10-09：Session 编辑边界

- 用户要求：修复 `WorkflowProgress is not defined`，中央只保留一个编辑入口，意图和手动输入合为一框。
- 前端 helper 合并到 `/workflow.js`，启动时构建、验证首页和脚本，兼容仍运行旧静态路由的服务。
- 已创建 Session 按 Run ID 存草稿；未开始的新 Session / 新工作流有独立 draft ID。
- 输入、生成 job、任务配置、向导步骤与幂等请求均随编辑上下文，迟到异步回复只写回发起方。
- 新 Session 使用已保存流程和空需求；采用生成/模板编辑当前工作流，保存新版本，下次运行生效。
- 旧全局草稿缺少可靠归属，恢复为独立草稿；原浏览器记录和原生历史都保留。
- 当前边界：同一浏览器内隔离，不提供跨设备草稿同步或同一 Session 的多人并发编辑合并。

## 2026-10-09：原 Session 续作与运维

- 编辑需求与选定任务说明后续作，不调用新建 Run / slot 或重新克隆代码库。
- 续作保留配置快照；工具、模型、Effort 和任务顺序的修改仍保存为下一版工作流。
- 运行中的任务先停止并核对原生状态。停止不会回滚已写入的源码。
- 原生 `spawn_continue` 优先续接；明确无法续接时允许按已有协议重建子任务，父 Session 和源码目录不变。
- 关闭与永久删除分别展示；删除要求完整 Session ID 和有效备份，不清空源码、审计或其他 Session。
- 实现、接口、恢复边界与手动启动说明见 [原 Session 续作与运维](SESSION-OPERATIONS.md)。

# Octopus V2 实施路线与验收

日期：2026-10-09  
状态：原设计路线保留；用户已授权启动独立的 MVP-1.0.0 研发版。
当前实施与实际验证边界见 [MVP-1.0.0 计划](../MVP-1.0.0-PLAN.md) 和 [Release](../MVP-1.0.0-RELEASE.md)。
本文各阶段是验收目标，不表示其中所有原生契约和 Team 部署都已经通过。

目标是先得到一个本机可恢复、可解释的研发闭环，再覆盖当前四后端和管理功能。
沿用现有 KiroCrew 安装与原生接口；所有破坏性/故障实验使用专用数据和隔离的测试会话。

## 阶段 0：验证边界，确定能否按推荐架构实施

先编写最小的原生契约实验，不先铺开新 UI 和数据库功能。

| 编号 | 实验 | 通过标准 |
|---|---|---|
| K01 | 应用服务通过原生 HTTP 创建子任务 | 真实 Task 归属于指定原父 Session；agent、model、Effort、cwd 的请求与结果可核对 |
| K02 | 父 Chat 正在处理业务工具调用时派发 | 命令先返回可查询回执；无 Session 自锁，无重复派发；失败显示明确原因 |
| K03 | 产品 MCP 的可信 Session 绑定 | A 会话不能通过改变参数冒充 B；不向外部工具转交 Gateway owner 凭据 |
| K04 | 完成、权限、Chat 与 Web 反馈 | 权限仍可在 KiroCrew 处理；业务状态一致；父 Chat 不再次执行旧调度协议 |
| K05 | 同参 continue 与改参新 Attempt | 同参能力按原生结果处理；改模型/Effort 后原父 Session、Workspace 不变，真实配置可证明 |
| K06 | 停止、关闭、恢复 | 原生任务确实结束才确认停止；备份失败不删除；已关闭会话可按原 ID 恢复 |
| K07 | 回执丢失、断连、原生重启 | 无重复派发，无法确定时显示 unknown；不使用模型自述推断任务完成 |

K03 特别重要：当前代码将部分身份信息限定给原生受管理 MCP；
不能推断普通外部 MCP 已经支持同等绑定。先验证实际扩展/注册方式。
如现有接口不足，提交最小、明确的产品扩展或上游接口设计；
不把由客户自己编写接入代码作为通过标准。

交付：契约测试、受支持安装包指纹、脱敏事件轨迹、每个实验的实际结果。
只有边界通过，才按该路径继续。不能因为路由存在就跳过实验。

## 阶段 1：单后端的完整纵向闭环

建设：

1. 提取 domain/application/infrastructure/interfaces 边界。
2. 建立 SQLite schema、迁移版本、命令回执、事件、预期版本检查。
3. 接通一个已通过契约实验的后端。
4. Workspace 准备 → Attempt 派发 → 原生结果 → 交接核对 → 状态报告。
5. Chat MCP 与 Web 使用同一命令处理函数；CLI 成为兼容客户端。
6. 前端按 Session 订阅 SSE，断线根据事件序号补读或重新拉取快照。

验收：

- 从 Chat 开始，Web 能观察；从 Web 操作，Chat 查询同一对象得到同一版本。
- 重复命令不会生成重复 Run/Attempt；同时保存返回明确冲突。
- 用户给出仓库后，编码开始前已有真实源码、来源与可执行目录。
- 关闭浏览器、后台服务重启不会丢任务；恢复先查询原生状态。
- 一条真实开发任务完成，代码、diff、验证命令和结果能逐项追溯。

## 阶段 2：原 Session 续作与 Task 换模型

建设：

- ExecutionRevision 与 Attempt 配置快照。
- Task 编辑面板合并任务说明、工具、Model、Effort。
- 任务重试与下游失效规则；状态与进度按本次有效验收计算。
- 并发修改和停止/重试竞争处理；一个 Workspace 同时只有一个写入 Attempt。
- 主/子 Session ID 与稳定业务 Task ID 分开展示。

验收：

1. 失败 Task 换模型并重跑：Run、父 Session、Workspace 路径不变。
2. 旧 Attempt 的模型、日志、交接完整可查，新 Attempt 使用新配置。
3. 显式模型被后端替换时显示不匹配，不以代码测试通过代替参数核对。
4. Effort 未报告显示未知；不复制请求值伪装成实际值。
5. 旧 Attempt 迟到完成，不能把新 Attempt 标成成功。
6. 停止后再次续作使用新的命令 ID；发送结果不明时不盲目再发。
7. 已完成 Session 可继续改进，但重跑范围和下游失效在提交前说明。

## 阶段 3：覆盖四后端及完整开发流程

建设：

- Kiro / Claude / Codex / OpenCode 能力目录和版本化适配。
- 原生配置、Skills/MCP、认证就绪状态展示，区分配置与实际执行证据。
- 顺序流程、模板、意图生成草稿、导入导出。
- Candidate、测试、Review、交付报告之间的关联。

验收：

- 真正运行“规划 → 编码 → 审查 → 交付”四阶段，保存原生 Task、backend、参数和工具 Session 证据。
- 更换工具后，不保留另一工具不支持的模型或 Effort。
- 下游读取的是同一候选的真实 diff 和源码，不仅是上游总结。
- 交付阶段改动受审内容后，旧 Review 失效，最终状态不能继续显示已审查通过。
- 模型拒绝、认证失效、Shell 权限拒绝等在 Chat/Web 两端展示同一个错误状态。
- 导入导出的配置通过统一 schema 校验，任务 ID 与工作流名称不会冲突。

## 阶段 4：运维、迁移和可交付性

建设：

- 停止/关闭/重新打开/删除，备份与审计。
- 原有工作流、Run、任务证据和父 Session 的只读导入与管理权切换。
- 启动、升级、回滚、配置来源和诊断说明。
- 故障注入、恢复演练、数据保留与导出验证。

验收：

- 不关闭或删除其他 Session，原源码不会被“删除父对话”顺带清理。
- 恢复备份后能解释每个 Attempt 的配置、上下文、证据和原生归属。
- 旧 Run 的接管过程保留原 ID 和路径，没有新旧两个调度者同时推进。
- 服务崩溃点覆盖：命令保存前/后、派发前、派发回执丢失、结果到达后、验收写入前/后。
- 存储满、文件缺失、数据库忙、事件重复/乱序时有确定状态和恢复说明。
- 从干净分发包完成安装与真实开发闭环，不依赖开发者机器的绝对路径。

完成这些验收后，才把本地版本称为可日常使用的单用户 MVP。
多人、远程 Worker、EC2、Connector 不包含在这项声明中。

## 后续阶段：Dev Teams 与部署

本地闭环通过后，再按独立验收推进：

1. PostgreSQL、多用户授权、项目范围查询和事件订阅。
2. 隔离 Worker、工具身份、Workspace/Memory 与凭据隔离。
3. EC2 实验及访问控制、备份、升级与恢复。
4. GitHub/GitLab Connector，绑定候选的 PR/MR 和状态回写。

数据库换成 PostgreSQL不等于完成团队隔离；每个业务动作、事件流和产物下载都要校验主体与项目。
云资源创建和远端发布应作为单独实施任务。

## 首个可演示故事

用户在 KiroCrew Chat 输入仓库和目标，平台生成可编辑工作流。
用户确认任务与模型后开始；Web 实时显示源码准备和真实任务进度。
编码任务失败，用户直接在 Chat 或 Web 改模型续作，原 Session 和 Workspace 保留。
审查读取真实 diff；交付报告显示每次 Attempt 的请求配置、实际配置与验证结果。
随后强制停止、重新打开并继续，状态在服务重启后仍可恢复。

这个故事通过真实契约与故障实验后，再扩大模板数量和界面装饰。

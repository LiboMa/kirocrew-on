# 续作是怎么工作的

续作就是：在**同一个会话、同一个工作区**里，修改需求或某个任务，然后**从这个任务开始往后重新执行**。已经完成、而且不受影响的成果保留；
会话分支上的候选提交在原地延续，不会从头再来。

HTML 版：`docs/continue.html`（内容相同，带流程图）。以 2026-10-23 的代码为准（`octopus/domain.py` `operate("continue")`、`rerun_plan`、
`octopus/chat_changes.py`、`octopus/engine.py`）。

## 1. 什么时候用续作

| 你想 | 用什么 |
|---|---|
| 结果不满意，改需求或某个任务的说明，从那个任务起重做 | **续作** |
| 换一个任务的工具、模型或 Effort | **续作**（改该任务的执行设置） |
| 在 KiroCrew 聊天里改过之后，回到平台继续 | **续作**：平台会先提交聊天里的改动（§5） |
| 任务正在运行，想插一句话（只限 Kiro 任务） | 补充说明 |
| 会话失败了，想让协调者诊断并自动纠错 | 请求诊断 |
| 本机改了代码，想让远端接着检查与审查 | 本地同步（`octopus sync`） |
| 换一个全新的需求 | 新建会话 |

## 2. 从哪里续作

| 入口 | 写法 |
|---|---|
| 控制台 | 会话页任务卡片上的「续作」，在对话框里填「本次完整需求」「任务名称」「任务说明」、执行设置与契约字段，并勾选要重跑的后续任务 |
| MCP | `octopus_continue`（`run_id`、`task_id`，可带 `input`、`execution`、`rerun`、`recovery`） |
| CLI | `octopus continue <任务> [--input 需求] [--prompt 说明] [--tool 工具] [--model 模型]` |
| API | `POST /v1/runs/<id>/continue`，见下 |

```json
{
  "request_id": "8–100 字符，重发同一个请求不会重复执行",
  "expected_version": 7,
  "task_id": "code",
  "input": "本次完整需求（可选，不写则沿用）",
  "execution": {"tool": "codex", "model": "auto", "prompt": "……", "verify": ["pytest -q"]},
  "rerun": ["review"],
  "recovery": {"enabled": true, "max_cycles": 2}
}
```

- `execution` 可覆盖的字段：`name`、`tool`、`model`、`effort`、`prompt`，以及任务契约（kind、role、deliverables、acceptance、verify、paths、skills 等）。
- `rerun` 列出之后的任务里**要**重跑的；不写表示之后的全部重跑。

## 3. 平台收到续作后做什么

<!-- html: figures/continue-flow.html -->

按顺序：

0. **先提交聊天里的改动**（D73）：工作区里有不在候选提交里的改动时，先把它们提交成新的候选（§5）。
1. **检查能不能续作**，不满足就当场拒绝并说明原因：

   | 检查 | 不满足时 |
   |---|---|
   | 版本号等于会话当前版本（防止基于过时的页面续作） | `409 version_conflict`「Session 版本已更新」 |
   | 会话已停下（完成、需要处理、失败、停止）并处于打开状态 | `409 busy`「请先等待结束或停止」 |
   | 所选任务之前的任务都已交接 | `409 dependency`「先完成上游 Task」 |
   | D49：个人执行边界上只有边界的主人能续作；Team 未归档 | `403 boundary_owner_only` 等 |
   | 审查独立：改完之后，审查任务不能用被审查改动的作者工具 | `400`「审查不独立：……」 |

2. **改任务**：
   - 把你写的覆盖字段合进所选任务；
   - 你换了工具或模型时，原计划里「需求原文指定的工具 / 模型」让位给你的选择；
   - 只写了 `verify` 时，它同时成为必过检查。
3. **决定重跑哪些任务**：
   - 所选任务一定重跑；
   - 没有勾选时，之后的任务全部重跑；
   - 勾选了一部分时，下面几类仍会重跑，并标明原因：
     - 还没交接的；
     - 依赖了某个重跑任务的；
     - 在重跑任务之后的审查与测试，因为它们的结论基于旧代码；
     - Knowledge。
   - 其余标为「沿用」，结论保留。
4. **改需求**：需求变了时，规划阶段补全的需求被标为「已过时」，之后的任务会被告知以新需求为准。
5. **重新计算纠错预算**：协调者的轮数、自动重试的次数与时长，都从这一刻起算。
6. **会话回到「待执行」**（执行环境不可用时为「等待执行环境」）。
7. **记一条修订**：续作「任务名」——改了什么、重跑哪些、沿用哪些。修订历史里可以任选两版对比。

## 4. 之后 Engine 怎么跑

- **顺序**：从第一个未完成的任务开始，一个接一个，与新会话相同。
- **新的尝试**：每个重跑的任务是一次新的尝试：
  - **新开一个子 Agent**：用户的续作不续接原来的子 Agent 对话，因为需求或任务说明可能已经变了。只有平台自动返工时，才在原对话上续接。
  - **在同一个工作区、最新的候选提交之上工作**；它的改动从这个候选算起，记到它自己名下。
  - **拿到上游任务的交接摘要**；审查绑定最新的候选。
  - **照常把关**（交接、改动、秘密、检查命令、Evaluator），失败时照常自动纠错。
- **沿用的任务**：不再执行，结论保留。

## 5. 与 KiroCrew 聊天的衔接（D73）

在 KiroCrew 聊天里，你可以直接让父会话的 Agent 改工作区、派子 Agent。回到平台续作时：

1. 平台比对工作区与会话分支上的最新候选。有不在候选里的改动，或候选之后的新提交，就把它们提交成新的候选。
2. 这次提交记为「对话中的改动」：挂在最后一个写代码的任务上，照常做秘密检查。
   - 这个任务这次不重跑、又有检查命令时，先跑检查命令；
   - 它之后的任务重新执行，审查针对新的候选；
   - 修订摘要以「对话中的改动：N 个文件」开头。
3. 有疑似凭证或 `.env` 时拒绝续作（`409 chat_secret`），会话分支不动，列出文件，请先在聊天里移除。
4. **聊天里改了行为，续作时要把「本次完整需求」改成新的需求。**
   之后的审查与 Evaluator 以会话的需求为准。需求没改时，它们会把聊天里的改动判为不符合需求，协调者再安排返工把它改回去。
   EC2 run-588bc3d5（2026-10-23）就是这样：聊天里把问候改成「你好呀」，续作时需求没改，审查判为需要修改，返工改回了「你好」。
   父会话的 Agent 在帮你总结时，会对照需求原文写出「需求有变化」和续作时应填的新需求。

**为什么必须先提交：**
- 审查结束时，平台会把审查期间工作区的变化「放回」到候选，包括未提交的改动和候选之后的提交，所以聊天里的改动会被还原；
- 如果下一个是实现任务，聊天里的改动会被算成它的改动。

先提交成候选，两种情况都不会发生。

## 6. 保留什么、替换什么

| 内容 | 续作之后 |
|---|---|
| 工作区与会话分支 | 保留，原地延续 |
| 沿用的任务 | 结论保留 |
| 重跑的任务 | 新的尝试替代当前结论；以前的每次尝试都留在历史里 |
| 子 Agent 对话 | 重跑的任务新开；原对话仍可在原生页面查看 |
| 纠错预算 | 从续作时重新计算 |
| 修订历史 | 新增一条 |
| 已发布的 Draft PR | 开启了自动发布时，续作完成并通过门禁后按新版本再发布一次（每个版本一次）；否则在会话页再发布 |

## 7. 常见问题

**提示「Session 版本已更新」？** 会话在你打开对话框之后变了，比如平台追加了 Evaluator，或别人刚续作过。刷新后重来。

**为什么不能从第 3 个任务续作？** 它之前有任务还没交接。先续作那个任务。

**我没勾审查，它为什么还是重跑了？** 审查与测试在重跑的任务之后时，旧结论对新代码无效，所以一定重跑，原因会标在对话框里。

**续作会不会覆盖我在聊天里改的？** 不会。续作先把它们提交成新的候选，之后的任务在它之上工作（§5）。

**我在聊天里改的，续作之后又被改回去了？** 多半是需求没跟着改：审查按会话的需求判定，认为改动不符合需求，协调者就安排了返工。续作时把「本次完整需求」改成新的需求再提交（§5 第 4 条）。

**续作和请求诊断有什么区别？**
- 请求诊断：不改任务，让协调者读失败证据，自己决定重试、返工、换工具或重新规划。
- 续作：由你来改。

**续作要花多少？** 只有重跑的任务会再用模型；沿用的不花。

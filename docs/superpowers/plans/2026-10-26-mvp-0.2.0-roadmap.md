## 2．分期、前提与验收

**每期的规矩**（设计 §15）：单独评审 → 本机回归（`tools/regress.sh`）→ E2E → EC2 验收 → 合并。

| 期 | 做什么 | 开工的前提 | 谁来定 | 验收 |
|---|---|---|---|---|
| **P0 实测** | E §5 的 T1–T12，加 CE 审阅要求的 T13（设计 §16），在一次性的测试资源上进行 | 负责人批准创建测试资源（≤ $20），并配合 T5 的设备码登录 | 负责人（§17 #13） | 得到实测值并回填设计；**T5 不通过则 P3 不开工** |
| **P1 打底** | 设计 §15 P1 的 ①–⑪，用户体验不变 | 无。其中要建 AWS 资源的 ⑤⑨ 与要排空 EC2 的 ⑩，各自在步骤里说明前提 | — | 见 P1 计划各任务；EC2 部署后控制台、会话、MCP、原生入口的行为不变 |
| **P1b KiroCrew 升级**（只在需要时单列） | P1 ⑩ 做不到「不改变用户体验」时拆出 | ⑩ 的评审结论 | 负责人确认用户可见的变化 | 同 P1 ⑩ |
| **P2 单机版一键安装** | `install.sh`（AL2023 / Ubuntu × arm64 / x86_64）、pip、Docker、源码；CloudFront 小栈；控制台的 Kiro 设备码；部署套件外部驱动 | P1 的打包与 ARM64；新开测试 EC2（需批准）；§17 #9 发布渠道（按默认推进） | 负责人批准新开机器 | 四种组合各在新 EC2 上一条命令装通，并跑通一个真实会话（设计 §15 P2） |
| **P3 集群版底座（只开放给管理员）** | 部署套件两步；数据面栈；主机代理；主机加入；用户卷；槽位端口；通配原生入口与 Host 路由；迁移编排 | P0 的 T5、T6、T13 通过；§17 #1、#2（#8 已定：不另购域名，按设计 §8.2a 隔离） | 负责人 | 两台池主机之间迁移 20 次，p95 ≤ 60 s；主机故障与 UUID 篡改演练 |
| **P4 自助申请与切换** | 控制台申请（共享 / 专用）、写入认证信息、设备码、切换、回收、扩容 | P3 验收；§17 #3、#4、#5（W3）、#14 | 负责人 | ≥ 3 个测试用户；有会话运行时双向切换 |
| **P5 迁移现有部署与温备** | `personal` 退役、m1 上的边界搬到用户卷、授予控制面权限、Litestream、温备与演练 | P4 验收；§17 #2、#5（W4、W12）、#6 | 负责人 | 搬家后会话继续、依赖自动重建、不用重登；RTO ≤ 15 min、RPO ≤ 5 s |

# MVP 0.2.0 P2 单机版一键安装 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** 用户在自己的一台 EC2 上执行一行 `install.sh`，就得到一套可用的 KiroCrew ON 单机版：控制台、主人的边界、Kiro 在控制台用设备码登录、需要时在控制台新建同机边界。

**Architecture:**
- `install.sh` 预检系统与架构，取发布物并验签，再执行与 OS 无关的安装步骤。步骤从 `al2023.sh` 拆出，按 dnf / apt 分支。
- CloudFront 用一个小栈，由安装时的凭证建立。装完后主机角色只保留 Bedrock 权限；之后的 AWS 写操作由部署套件在主机外执行（S29）。

**Tech Stack:** bash（AL2023、Ubuntu）、Python 标准库、CloudFormation、React 控制台。

**Spec:** `docs/superpowers/specs/2026-10-25-mvp-0.2.0-deployment-and-worker-pool-design.md` §4.1–4.2、§4.4、§6.4、§15 P2；决定 S25、S26、S29、S30、S31，以及 §8.2a（同一个域名）。

## Global Constraints

- **支持矩阵**：AL2023 与 Ubuntu 22.04 / 24.04，各支持 aarch64 与 x86_64。
  - x86_64 照装，开头和结尾各提示一次「推荐 ARM64（Graviton）」；
  - 其他系统列出受支持的系统后以退出码 2 结束；
  - 不在 EC2 上（IMDSv2 不可达）时说明原因后退出；
  - 资源门槛：root 或 sudo、systemd、空闲磁盘 ≥ 40 GiB、内存 ≥ 8 GiB。
- **每一步可重跑，只补缺**；现有 EC2 的 `deploy.sh push` 路径（`al2023.sh`）行为不变。
- **发布物先验签再用**：`manifest.sig` 用内嵌公钥、openssl 验证；wheel 的 sha256 与清单一致。不提供只校验哈希的退路。
- **KiroCrew**：S26 的前提（升到正式版）要等 P1b；在那之前照 `deploy/versions.env` 钉住的提交从源码构建，清单里注明来源。
- **凭证**：
  - AK/SK 只在本进程中使用，不写盘、不写进配置；
  - 装完核对主机角色只剩 Bedrock 调用权限，否则打印要卸下的策略；
  - 源站密钥在本机生成，只写本机 0640 文件。
- **安全底线**：同一个域名按 §8.2a；所有 Cookie 一律 `__Host-`；设备码只给边界主人看，不进审计和日志（§6.4）。
- **新增等待与门槛**：用户体验里任何新的等待或确认，都要先经负责人批准（no-gates-without-owner）。
- **文案与命名**：中文；文档与代码注释里不点名参考过的站点。

## Review Focus

1. **重跑**：中途失败（网络、凭证、磁盘）后再跑一次，结果与一次跑通相同，不会重复建栈、建用户、换密钥。
2. **验签失败、清单与 wheel 不符、频道里没有该版本**：都停在任何改动之前，并说明原因。
3. **设备码登录与多人**：同一台主机上，A 的设备码只出现在 A 的页面上；B 的登录状态不受 A 的登录影响；登录进行中再点一次，不会起第二个进程。
4. **新建边界的提权面**：API 进程只能用已校验的参数调用 root 步骤（名称、属主），不能借它执行其他 root 命令。
5. **Ubuntu 22.04 没有 Python 3.12**：用 uv 管理的 CPython，`kirocrew-on` 与 KiroCrew 都能运行；AppArmor 代替 SELinux 的步骤不报错。

  - x86_64 打印推荐 ARM64 的提示；
  - IMDSv2 不可达时退出并说明原因；
  - 磁盘或内存不足时退出。

### Task 5: 控制台里的 Kiro 设备码登录（§6.4）

**Files:**
- Modify: `octopus/worker.py`（`/kiro/login` 起一个 pty 运行 `kiro-cli login --use-device-flow`，Worker 本就以边界用户运行，不需要 root；`/kiro/login/status`）、`octopus/domain.py` 与 `octopus/server.py`（`POST /v1/workers/<id>/kiro-sign-in`、`GET` 状态：只给该边界的主人）、`octopus/schema.py`、`web/src/features/settings/`（「我的设置 › 执行环境」的「登录 Kiro」）
- Test: `tests/test_kiro_login.py`、控制台 vitest

**Interfaces:**
- Produces：
  - 平台返回 `{state: "waiting" | "done" | "failed", url, code, expires}`；
  - 设备码不写审计、不写日志；
  - 同一时间每个边界只有一个登录进程；
  - 已登录时直接返回 `done`，不起进程。
- [x] 测试：
  - 用假的 `kiro-cli`（打印验证地址与设备码，过一会儿退出 0）跑通整个流程；
  - 非主人（含管理员）拿不到设备码；
  - 登录进行中再请求，返回同一个码，不起第二个进程；
  - 审计与日志里没有设备码；
  - 控制台显示地址与码，登录完成后提示「已登录」。
- [x] 实现，然后运行测试；提交。

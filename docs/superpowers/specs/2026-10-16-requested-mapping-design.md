# 映射策略：需求中指定的工具与模型（D45，M2）

## 1．目标

M2 验收 2「Prompt 中指定的映射被采用并标注来源；不可用的指定给出原因，不静默替换」；MVP 验收矩阵「Prompt 指定 Agent：指定优先于策略；
能力不支持时明确拒绝并说明」。现状：KiroCrew 规划时被告知「available 为 false 的工具不要选择」，用户在需求中点名一个不可用的工具时规划者会
换成别的；规划结果中未公布的模型被平台改为 `auto`（只记一条说明）；映射来源只写「KiroCrew 规划」，看不出哪些是用户点名的。

## 2．已确定（负责人方向：开发质量与 Agent Harness 优先，非必要不确认）

| 编号 | 决定 |
|---|---|
| Q1 | 由规划者识别需求中的指定（自然语言）：任务带 `requested: {tool?, model?, quote}`（`quote` 为需求原文片段，≤200 字符）。平台不解析自然语言。 |
| Q2 | 平台照指定执行：规划结果的工具 / 模型与 `requested` 不同时改回指定（记说明）；指定的模型未公布时**不**改为 `auto`。 |
| Q3 | 指定的工具不可用或模型未公布：派发前拒绝，会话 `blocked`，写明「需求指定的 …」；不交给协调者、协调者也不得换工具——由用户决定（修复执行环境后续作，或续作时改用可用的工具）。 |
| Q4 | 续作时用户改了该任务的工具或模型：新的选择取代需求中的指定（`requested` 去掉）。显式提交的 steps / 工作流不受本期影响（D38 照旧）。 |

## 3．设计

- **规划提示**（`plan_step`、`replan_step`）：需求明确指定某任务的工具或模型时，照指定写 `tool` / `model` 并写 `requested`（即使该工具 `available` 为 false，
  平台会如实告知）；没有指定时省略 `requested`。
- **校验**（`domain.steps`、`workflow_import.normalize`）：`requested` 为对象，`tool` ∈ 工具列表、`model` 为字符串（≤200）、`quote` 为字符串（≤200），
  至少有 `tool` 或 `model`。
- **追加**（`planning.expand`）：`requested.tool` 与 `tool` 不同 → 改回并记「任务「…」改回需求指定的工具 X」；`requested.model` 未公布 → 保留并记
  「需求指定的模型 X 未由执行环境公布」。
- **派发**（Engine）：带 `requested` 的任务，工具在执行环境记录中不可用，或指定的模型不在公布列表 → `_refused`：Attempt `blocked`，
  `error`「需求指定的 claude 在此执行环境不可用：…」/「需求指定的模型 X 未由执行环境公布」，证据 `failure_type: tool`、`requested: true`。
- **恢复**：`schedule` 对 `requested: true` 的失败不安排诊断；`recovery.switch` 拒绝为 `requested.tool` 与当前工具相同的任务换工具。
- **可见**：映射来源「需求中指定：「quote」」（截 30 字）；`attention`「需求指定的工具或模型不可用」——「修复执行环境后续作，或在「配置并续作」中改用可用的工具或模型」。

## 4．测试与验收

- **本机**：规划给出 `requested`（可用）→ 照用、来源为「需求中指定」；规划者改了工具 → 改回；指定不可用的工具 → 派发前拒绝、不诊断、写明原因；
  指定未公布的模型 → 保留、派发前拒绝；续作改工具 → `requested` 去掉后照新选择运行；`requested` 的校验；提示含说明。
- **EC2**：需求写「审查用 codex」的规划会话：审查任务的来源为「需求中指定」并由 codex 执行；需求点名一个未公布的模型：会话停下并写明原因，未改用其他模型。

# 一般任务：任务类型不与 Git 强绑定（D65，设计稿）

日期：2026-10-22。负责人：「做一个修正，任务类型并不和 Git 做强绑定，也可以做一般性多 Agent 任务处理；请做好 Plan 和 Design 和实施」。
标「（设计者决定）」的是负责人未逐条确认、由设计者定的，验收后可调整。

## 1. 为什么

今天平台的每个环节都假定「会话 = 改一个代码仓库」：
- 来源只能是「已有 Git 仓库」或「新建项目」，且必须选一个；
- 任务类型只有 implement / review / test / deliver / design；
- 规划提示写「研发任务」「源码检出」「paths」「verify」「.gitignore」「PR」；
- Agent 指令写「本次研发任务」「源码目录」「改动文件」；
- 交付只有 Git 发布。

调研、分析、写作、方案这类工作也被按代码处理。EC2 上已出现的后果：
- 调研报告一次出不来；
- 审查者改动交付文档被撤回（run-b0b3d23c）；
- 交付文件未提交（run-9dce9610）；
- 幻灯片任务的重规划被页数检查耗尽（run-8e02f71d）。

这些都是 BACKLOG 与 D57 的现场。

## 2. 目标与不做

- **目标**：一个会话可以完全是一般工作，由多个 Agent（Claude Code、Codex、Kiro）分步完成，产出是工作目录中的文件或交接中的结论；
  研发会话照旧。同一会话里两类任务可以混合（例如先调研、再实现）。
- **不改**：研发任务的门禁、Evaluator、Knowledge、发布与 D57 的语义；工作目录在 Worker 上仍以 Git 记录每次 Attempt 的版本（内部机制，
  使用者看不到、也不需要仓库）。
- **不做**（设计者决定）：
  - 任务并行；
  - 内置的一般任务工作流模板（no-hardcoded-chains：由 KiroCrew 规划者按需求编排）；
  - 控制台内的 Markdown / Office 渲染（产出可下载；记 BACKLOG）；
  - 一般任务的自动 Evaluator（见 §4）。

## 3. 不需要代码仓库的会话

- 新来源 `{"type": "none"}`：「不需要代码仓库」。Worker 为它准备一个空的工作目录（与 `new` 相同：平台发给 Worker 的是 `new`，旧 Worker 也能
  执行）；会话页、报告与 Agent 指令把它叫「工作目录」，不叫「源码」。
- 与 `new` 的区别：
  - 不提供「发布到仓库」：409 `no_repository`，提示「此会话没有代码仓库：产出在会话页下载」；
  - 「下载源码」改为「下载产出」（同一份归档）；
  - Knowledge 与按仓库的准入规则照旧不适用。
- `octopus pull` 仍可取回工作目录（它本来就是一个分支）；`octopus sync` 照旧要求快进。

## 4. 一般任务的类型

新增两种 `kind`（设计者决定：两种足够规划者区分「找与想」和「做出成品」；比一个笼统的 general 更好写验收）：

| kind | 含义 | 产出 |
|---|---|---|
| `research`（调研） | 收集、阅读、比较资料与数据，形成发现与依据 | 发现文档（如 findings.md）或交接中的结论 |
| `write`（撰写） | 产出成品：报告、方案、文档、清单、幻灯片源稿等 | `deliverables` 写明的文件 |

- 门禁（与 `deliver` 相同的一档）：
  - 工作目录的快照作为本 Attempt 的版本，供后续审查绑定；
  - 什么都没写只是提示（`diff_present` 的 warn）；
  - `no_secrets` 照旧阻断（安全底线）；
  - 只有写了 `paths` 才检查改动范围；只有写了 `verify` 才运行检查命令；
  - 不跑基线测试。
- `review`（审查文档）与 `design`（分析与方案）照旧可用于一般任务：
  - 审查者不改被审查的文件（改动由平台撤回，D57），审查意见写成新文件或写在结论中；
  - 「改了被审查的文档」从错误变为可预期：审查要修改时写 `changes_requested`，交回 write 任务返工。
- **Evaluator**：照旧只在有 implement / deliver 的会话追加（设计者决定：一般任务的验收由规划中的 review 任务承担，不额外加一道门；负责人
  反映过「一次出不来」）。
- **Knowledge**：一般任务不写仓库知识（它按仓库组织）。

## 5. 规划与 Agent 指令

- **规划者**（`intent_prompt`、`planning.rules`）：
  - 意图写成「研发任务或一般任务（调研、分析、撰写等）」；
  - 研发任务的那几条（检出、paths、verify、.gitignore、PR、改代码的 evaluator）只对改代码的任务；
  - 一般任务用 research / write / review / design，`deliverables` 写产出文件名，`acceptance` 写阅读即可核对的标准，不必写 `paths` 与 `verify`；
  - 来源为 `none` 时明确告诉规划者「本会话没有代码仓库」。
  - 提示长度：首次规划不超过现有上限（`tests/test_replan.py` 7400 / 7800）。
- **Agent 指令**（`worker.envelope`）：
  - 一般任务的标题是「本次任务」，目录写「工作目录」；
  - research / write 的结尾：「把产出写成工作目录中的文件，交接写产出、依据与未完成项」；
  - 交接要求对一般任务写「产出、依据、未完成项」，研发任务照旧。
- **角色**：不新增（设计者决定）；一般任务可以不带角色，或用 spec 等已有角色。

## 6. 入口

- **控制台**：
  - 发起向导的来源多一项「不需要代码仓库（调研、分析、写作等一般任务）」；需求占位换成一般任务也适用的例子；
  - 任务类型标签加「调研」「撰写」；
  - 来源为 `none` 的会话页不显示「发布到仓库」、按钮写「下载产出」；
  - 一般任务的 Attempt 改动区写「文件改动」。
- **MCP**：`octopus_start` 的 `source` 接受 `{"type": "none"}`，说明里写明一般任务；Skill 同步。
- **命令行**：`octopus submit --no-repo`（来源 `none`）。

## 7. 验收

- 本机：
  - `none` 来源的校验、发布 409；
  - research / write 的门禁（没写文件只提示、秘密阻断、无 verify 不运行检查）；
  - 规划提示的长度；
  - Agent 指令的标题与结尾；
  - 向导 / MCP / CLI 的入口；研发会话的行为与事件不变。
- EC2：一个 `none` 来源的会话，需求为「调研某主题并写一份报告」，由规划者拆成调研 → 撰写 → 审查，跨两种工具一次完成，产出可下载；
  另跑一个研发会话确认无回归。

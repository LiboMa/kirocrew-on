# 协调者的返工可扩大可改动路径（D54）

日期：2026-10-21。负责人要求「先出设计」（2026-10-21，选「要，先出设计」）。

> 状态：2026-10-21 已实现（负责人未反对、要求继续 Loop）。与设计的一处差异：`paths_add` 只用于重试 / 返工**失败的那个任务**（`locked_files` 是相对它的候选算出的），不给其他目标。

## 1. 起因

EC2 会话 run-25c7aaa7（M0 脚手架）：评估任务提出 F1–F4 四项缺陷，横跨 task-1、task-2、task-3-2、task-5-2 的交付物。协调者第 9 轮
把修复整体交给 task-3-2 返工，实现者照做，改动正确。但 task-3-2 的 `paths` 只列了鉴权相关文件，`artifacts_locked`
门禁（D37 §11.2）每次都拒绝「改动了已验收任务的交付物」。

协调者能做的只有 retry、rework、switch_tool、replan、wait_for_user：
- 都不能改任务契约；
- 重新规划的额度已经用完；
- 于是只能连续多轮 `wait_for_user`，13 轮后停住，等用户续作时手工扩大 `paths`（负责人选了路径 A）。

门禁本身没有错：它防止一个任务悄悄改动别人已验收的交付物。缺的是一个**有记录、有上限**的办法，让协调者在明确要求跨任务修复时，
把它点名的那几个文件交给返工的任务。

## 2. 目标与不做的

目标：
- 协调者的 `retry` / `rework` 决定可附带 `paths_add`，平台核对后扩大目标任务的 `paths`，门禁随之放行这些文件。
- 每次扩大都可见：修订历史、时间线、MCP、报告写明「协调者为任务 X 增加了可改动路径：…（原因）」。

不做：
- 不让协调者删减 `paths`，也不让它改其他契约字段（验收项、检查命令、类别、角色）。
- 不放开整个项目：通配符、目录、`.`、`**` 一律拒绝。
- 用户续作改 `paths` 的方式不变。

## 3. 规则

`paths_add` 是 1–10 个项目内的相对文件路径，**每一项都必须是门禁会锁住的文件**：此前已验收任务的候选提交里改动过的文件，
即 `Engine._locked` 计算的 `owners` 集合，平台检查运行留下的文件除外。

由此得到两条：
- 不能借它扩到与本会话已验收工作无关的文件。新文件本来就不受门禁限制，不需要加。
- 一个尚未验收的下游任务的文件也不需要加：门禁不锁它们，之后那个任务按依赖重跑时会复验。

核对不通过时，整份决定被拒绝，写明是哪一项（与换工具的核对相同，记 `refused`，协调者下一轮可见）。

## 4. 生效

决定应用时（`recovery.apply`），同一事务内依次：
1. 目标任务的 `spec.paths` = 原有 + `paths_add`，去重，总数不超过 20（超出则拒绝）。
2. 记一次修订，kind 为 `recovered`，摘要「协调者扩大 <任务名> 的可改动路径：a、b…」。这样下一次续作的修订对比，不会把它算成用户的改动。
3. 记时间线事件 `task.paths_added`，内容为 {task_id, added, reason, recovery}。

被改动交付物所属的已验收任务**不重跑**：
- 门禁放行后，返工任务交付的是合并后的结果；
- 之后的审查 / Evaluator 照常复验（review、test 在改动后必须复验的规则不变）。
- 是否需要重跑上游，由协调者的 `instructions` 和下一轮审查决定，与今天一致。

## 5. 协调者看到什么

- 只有失败门是 `artifacts_locked` 时，`context.coordination` 才多出 `locked_files`：门禁拒绝的文件及其所属任务（来自门禁的 detail）。
- 提示词加一句：这种情况下可在 `retry` / `rework` 决定中给出 `paths_add`（只能是 `locked_files` 中的文件），并在 reason 中说明为什么这些文件应由目标任务修改。
- 其余失败类型不提这个字段，以免协调者把它当成通用的放行办法。

## 6. 可见

- **控制台**：修订历史出现这条「自动纠错」修订，对比能看到 `paths` 的前后值；自动纠错面板的决定写明增加了哪些路径。
- **MCP**：精简状态 `recovery.latest` 带 `paths_added`。
- **Skill**：说明协调者可能扩大路径，以及这一做法的来历。
- **报告**：任务一节写「可改动路径由协调者扩大：…」。

## 7. 测试

- 门禁拒绝后，协调者给出 `paths_add`（来自 `locked_files`），返工通过，会话完成；修订与时间线各有一条。
- 以下情况整份决定被拒并写明原因：
  - 路径不在 `locked_files` 中；
  - 带通配符或目录；
  - 越出项目；
  - 超过 10 项，或合并后超过 20 项；
  - 用在 `switch_tool`、`replan` 或 `wait_for_user` 上。
- 失败门不是 `artifacts_locked` 时，`context` 里没有 `locked_files`。
- 回归：用户续作改 `paths`、D45 指定的工具与模型、审查独立性检查都不受影响。

## 8. 留给实现者

- `paths_add` 写在决定 JSON 顶层（与 `tool` / `model` 同级）。
- 核对放在 `recovery.py`，与 `switch()` 并列，返回扩大后的 spec。
- `locked_files` 的来源：
  - 首选：给门禁的 `fail` 记录加结构化字段 `files`，避免从中文 detail 里解析；
  - 旧证据没有这个字段：不提供 `locked_files`，协调者照旧 `wait_for_user`。

# 按阶段把关（D69，设计稿）

日期：2026-10-22。

负责人的问题：「为什么每次审查都需要门禁？这个设计是合理的吗？不应该是设计、发散、收敛时，才开始做门禁的？」

负责人选择了「按阶段把关（推荐）」：
- 发散阶段只保留安全底线；
- 设计阶段结束时把关一次；
- 收敛阶段只看必须通过的检查和最后一次 Evaluator 验收；
- 审查只看结论；
- 阶段由规划者给任务标注。

标「（设计者决定）」的是负责人未逐条确认、由设计者定的，验收后可调整。

门禁代码现由 D57（门禁减负，另一个会话）负责。本设计建立在 D57 之上，并保留它的 6 条约束（§3a）。

## 1. 为什么

门禁按「每个任务」统一执行，沿用自「每一步都必须可验证的代码开发」（D37）。

D57 之后，每个任务仍会阻断并进入纠错的检查有这些：
- `native_completed`：任务没跑完；
- `identity_match`：工具、模型或 Effort 与配置不符；
- `outcome_pass`：执行者或审查者写了 `blocked` / `changes_requested`；
- `review_bound` 的少数情形：平台未能撤回审查的改动；
- 无法生成候选；
- `no_secrets`；
- 必须通过的检查（`checks_pass`）；
- Evaluator 的 `evaluated`。

对头脑风暴、调研、多方案探索这类发散工作，逐步把关几乎没有价值，只会制造阻断、诊断和返工的循环。EC2 上的现场：
- 调研报告一次出不来；
- 审查交付文档被撤回（run-b0b3d23c）；
- 幻灯片任务的重规划被页数检查耗尽（run-8e02f71d）。

真正需要把关的是收敛点：设计定稿、交付物成型的时候。

审查给出「要修改」时返工，这是审查的职责，在需要把关的地方保留。

## 2. 阶段

任务新增可选字段 `phase`：

| phase | 含义 | 典型任务 |
|---|---|---|
| `diverge`（发散） | 头脑风暴、调研、多方案探索：产出是素材与想法 | research，探索性的 design |
| `design`（设计） | 形成方案并定稿 | design，对方案的 review |
| `converge`（收敛） | 实现、撰写、测试、交付：产出是成品 | implement / write / test / deliver，对成品的 review |

- **谁来标**：
  - 规划者在计划中标注；
  - 人在任务编辑器里可以改（「自动」即不写）；
  - 导入的工作流可以带。
- **没标时按类型推断**（设计者决定）：
  - research → `diverge`；
  - design → `design`；
  - review → 它所审查的任务的阶段：取 `depends_on` 中最后一个非审查任务，没有时取计划中它之前最近的非审查任务；
  - 其余（implement / test / deliver / write / 未写类型）→ `converge`。
  - 研发会话的任务因此都推断为收敛，行为与今天相同；变化集中在调研、设计这类会话。
- **平台自己的任务没有阶段**，照旧处理：
  - 规划、协调者重新规划；
  - Evaluator；
  - Knowledge 写入；
  - 工作流推荐（`purpose: workflow_design`）。
- **阶段末**：一个设计任务是「设计阶段末」，指在计划顺序里它的下一个任务不是设计阶段，或它是最后一个任务。
  - 按当前快照的任务顺序在判定时计算，所以重新规划之后照样成立。
  - 只有一个设计任务时，它就是阶段末，行为与今天相同。

## 3. 每个阶段检查什么

| 检查 | 发散 | 设计（中途） | 设计（阶段末） | 收敛 |
|---|---|---|---|---|
| 安全底线：`no_secrets` 与 D57 T6–T12 的扫描 | **阻断（安全拦截）** | **阻断** | **阻断** | **阻断** |
| 平台故障的自动重试（T13：runtime_sandbox / runtime_teardown / never_started） | 照旧 | 照旧 | 照旧 | 照旧 |
| `native_completed`：原生出错（`native_error`，重试后仍失败） | 提示 | 提示 | 阻断 | 阻断 |
| `native_completed`：被停止（`native_stopped`）、登录失效（`auth`）、归属不可核实（`lost`）、安全（`security`） | **阻断** | **阻断** | **阻断** | **阻断** |
| `identity_match` | 提示 | 提示 | 阻断 | 阻断 |
| `outcome_pass`（blocked / changes_requested） | 提示，结论交给下一个任务 | 提示 | 阻断，返工 | 阻断，返工 |
| 检查命令 | 不运行 | 不运行（design 本来不运行） | 不运行 | 只有必须通过的阻断（D57 §5） |
| 审查的撤回（D57 Task 3/3b）、`review_bound` | 照旧（撤回；提示） | 照旧 | 照旧 | 照旧 |
| Evaluator | — | — | — | 会话末统一验收一次（有 implement / deliver 时，照旧） |

- **「提示」的含义**：
  - 这一项记为 warn，任务按「已完成（有提示）」接受，会话继续；
  - 不进入协调者诊断，不消耗纠错轮次；
  - 下一个任务从交接里看到它的结论与未完成项（engine.handoff 已带 `decision`、`summary`）。
- **发散任务没跑完**：
  - 平台按 D57 §4 的方式生成一份交接，写明「任务未完成：<原因>；后续任务照常开始，缺少它的产出」；
  - 会话页在该任务上显示提示。
  - 不会静默完成（约束 2）。
- **审查的结论**：
  - 在设计阶段末与收敛阶段，`changes_requested` 照旧交回被审查的任务返工；
  - 在发散与设计中途，结论只记提示并交给下一个任务。
  - 程序上的问题（版本不符、改了被审查的文件）在所有阶段都只是提示（D57 已如此）。

- **可降级的失败是白名单**（D57 会话审阅，设计者采纳）：
  - 只有 `failure_type` 属于 `{native_error, tool, model}` 的失败，以及 `outcome_pass` 的失败（执行者或审查者的结论）可以降级；
  - `outcome_pass` 的结论类型若属于 `recovery.NEEDS_INPUT` 或 `environment`（缺输入、登录、模型、环境），需要有人处理，照旧阻断（设计者决定）；
  - 其余一律照旧阻断，以后新增的失败类型默认也阻断。原因如下：
    - 停止（人、管理员或看门狗）必须让会话停下；
    - 登录失效需要管理员处理；
    - 归属不可核实时，产出可能不属于这次 Attempt；
    - 安全命中由 D57 T8 拦截。
- **只有调研的会话里写了必须通过的检查**（设计者决定，D57 会话建议）：
  - 情形：D57 T5 会把缺失的继承检查放到一个能运行检查的任务上；发散任务不运行检查，所以可能一个能运行的任务都没有。
  - 做法：不判计划无效，记一条提示「必须通过的检查没有可运行的任务（发散阶段不运行检查命令）」。
  - 理由：负责人的方向是不给探索性工作设红线；要强制运行检查，就让规划者加一个收敛任务。

## 3a. 必须保留的约束（D57 会话，负责人规则）

1. **安全底线与阶段无关，必须拦住**。负责人：「安全底线，彻底一定要拦住！」「误报怎么处理，就停下来，人工处理，以后形成记忆」。
   - `no_secrets` 在任何阶段都不降级为提示：命中即进入安全拦截状态（D57 T8），不诊断、不自动重试，只由创建者、Team Owner 或管理员判定真密钥 / 误报。
   - D57 T6–T12 把扫描扩展到交接与结果文字、检查输出、预览与下载、未交付的补丁，这些在每个阶段都运行。
   - 本设计里「不阻断」只适用于非安全检查。
2. **发散任务的原生失败要有结果**：先走 T13 的平台故障重试；最终失败记为该任务的提示，并生成交接（§3），不静默。
3. **审查的撤回在所有阶段保留**：已跟踪文件的改动撤回，新建文件移到 `run/attempts/<id>/review-removed/`，否则审查者的文件会混进下一个候选。
4. **防空转（T13）以 `evidence["gate"]` 与第一条 fail 记录为键**：
   - 降为提示时，移除 `evidence["gate"]` 与 `failure_type`，并把 fail 改写为 warn；
   - 只有真正阻断的失败才保留它们，否则「同一原因两次」会认错。
5. **收敛复用 D57 T5 的钩子**：
   - `verify_required`、`verify_basis`、`origin: planner`、`domain.runs_checks()` / `required_checks()`；
   - 重新规划时补上缺失的继承检查。
   - 本设计不重新推导。
6. **D68 与 D57 Task 12（spec §7.4「有提示就不自动发布」）**：
   - D68 自动通过的待人确认项是提示，所以自动发布会等负责人确认。这是预期行为（负责人：推送须经负责人确认），写入运维说明。
   - D69 的提示同理：有发散 / 设计中途提示的会话，自动发布同样等确认（设计者决定，与 Task 12 一致）。

## 4. 记录与显示

- 降级的那条记录：
  - `status: "warn"`；
  - `detail` 前缀「发散阶段不阻断：」或「设计阶段中途不阻断（阶段末再把关）：」，后接原来的原因，原文保留；
  - `relaxed: "fail"`。
- Attempt 证据记录：
  - `evidence["phase"] = <阶段>`；
  - `evidence["phase_relaxed"] = <检查名>`；
  - `evidence["phase_relaxed_error"] = <原来的错误文字>`。
  - 移除 `gate` 与 `failure_type` 之后，只有这一项还记着原因：生成的交接与会话页的文案都用它。
- 任务状态为 accepted，`warnings` 照 D57 §4 列出。
- 会话页与报告：
  - 任务卡片显示阶段（发散 / 设计 / 收敛；推断的写「自动：…」）；
  - 降级的提示与 D57 的提示一样列出。
- 任务编辑器：「阶段」下拉，选项为「自动（按类型）/ 发散 / 设计 / 收敛」。

## 5. 规划与提示

- **规划规则**加一条（约一行，首次规划与重新规划仍受 `tests/test_replan.py` 的长度上限约束）：
  「phase：diverge 发散（头脑风暴、调研、多方案）只查安全底线；design 设计在阶段末把关；converge 收敛（实现、撰写、测试、交付）看必须通过的检查；可不写，按类型推断。」
- **Agent 指令**（`worker.envelope`）：发散任务的结尾加一句「发散阶段：写出发现与取舍，未完成项写在交接里；不必等全部完成」（设计者决定）。

## 6. 入口

- `domain.CONTRACT` 加 `phase`，取值校验为三者之一。
- OpenAPI 与 schema 写明 `phase`。
- 工作流导入接受 `phase`，别名「阶段」与中文值「发散 / 设计 / 收敛」规范化。
- MCP 的 `octopus_start` 与 Skill 说明 `phase`。
- 控制台：编辑器与会话页（§4）。

## 7. 实现要点（与 D57 T8 协调）

- **新模块 `octopus/phases.py`**：
  - `PHASES`；
  - `phase(spec, specs)`：推断；
  - `phase_end(task_id, specs)`；
  - `relax(evidence, spec, snapshot, error) -> str | None`：
    - 能降级时，就地按 §3a-4 改写记录与证据，并返回前缀；不能时返回 None；
    - 判定事务调用它，D57 T10（误报判定后重新判定）也调用同一个函数，不各写一份。
- **`engine`**：
  1. **检查命令**：在 `_more_gates` 取 `commands` 处，发散任务不运行检查命令（`checks_pass` 记为 skip「发散阶段不运行检查命令」）。
  2. **降级**：在判定事务里、自动重试已经决定之后（`if retry: … elif state == "blocked" …` 这条链，与 D46 P4 Knowledge 任务「不占住会话」同一处），加一个分支。
     - 条件：任务不是平台任务、不是安全拦截、阶段允许降级，且本次不是自动重试。
     - 处理：任务改为 accepted，按 §3a-4 改写记录，生成交接（原生失败时）。
- **与 D57 的分工**：
  - D57 T8（安全拦截状态）会改 recovery 的入口与 engine 派发的拦截，本设计不碰这两处；
  - 安全判定用 T8 导出的 `guard.blocking(evidence)`；T8 合入前原样内联同一表达式：`evidence.get("gate") == "no_secrets" or evidence.get("failure_type") == "security"`；
  - T8 不在判定链上加分支：安全拦截发生在判定链之前，`transient()` 对安全返回 None，`recovery.schedule` 跳过安全。共用的只有 `not <安全>` 这一个条件；
  - 实施前与 D57 会话交换 engine 的具体改动段。

## 8. 验收

- **本机**：
  - 推断规则（含审查继承所审任务的阶段）；
  - 阶段末的计算（重新规划之后）；
  - 发散任务的原生失败（重试后）、身份不符、blocked / changes_requested 都记提示，会话完成，没有诊断与纠错轮次；
  - 设计中途的审查「要修改」只记提示；设计阶段末的审查「要修改」照旧返工；
  - 任何阶段的 `no_secrets` 照旧阻断（T8 之后进入安全拦截）；
  - 发散任务不运行检查命令；
  - 研发会话（全部推断为收敛）的门禁记录与事件不变；
  - 规划提示长度；编辑器、导入、MCP 的 `phase`。
- **EC2**：一个调研会话（调研 → 方案 → 审查方案 → 撰写报告 → 审查报告），故意让调研任务的结论写 `blocked`。
  - 会话不进入纠错，报告照常产出；
  - 方案的审查「要修改」时返工方案；
  - 另跑一个研发会话，确认无回归。

## 9. 不做

- 不改 D57 的门禁语义与安全拦截流程。
- 不加并行任务。
- 不在一般会话追加 Evaluator（D65 §4 照旧）。
- 不在控制台做按阶段的进度视图（记 BACKLOG）。

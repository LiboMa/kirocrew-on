# 恢复阶梯第 4 期：等待与条件满足后自动恢复（D43，M2）

## 1．目标

设计 §8.1 的 L4：「缺源码 / 输入、认证过期、待批准、Worker 离线 → 进入等待，展示具体原因；条件探测满足后**自动恢复**；不计入预算」。现状：

- Worker / Gateway 暂不可用：M1 的退避会自动重试（不变）；
- 派发时 Kiro 登录过期（`tool_auth_expired`）：会话停在 `ready`，退避重发，登录恢复后自动继续（不变）；
- **运行中**的 Kiro 任务因登录过期失败（`failure_type: auth`）：会话 `blocked`，登录恢复后仍要人续作；
- Worker 被停用：运行中的会话 `blocked`「Worker 已停用」、准备中的会话 `waiting_worker`，重新启用后都不继续；
- 凭证被停用或不再可用：准备源码时 `blocked`，重新启用 / 更换后要人续作；
- 平台从不主动读取 Worker 的 `/health`：保存的执行环境能力（工具、命令、Kiro 登录）只在登记与「刷新模型」时更新，升级 Worker 后要手动刷新。

## 2．已确定（负责人方向：开发质量与 Agent Harness 优先，非必要不确认）

| 编号 | 决定 |
|---|---|
| W1 | 平台定期读取 Worker 的 `/health`（时限 5 秒）：有会话在等 Kiro 登录的 Worker 每分钟一次，其余已启用的 Worker 每 10 分钟一次；执行边界未变时保存为执行环境能力（与「刷新模型」相同），变了不保存。 |
| W2 | Kiro 登录：只有在失败之后**看到过**登录过期（`tool_auth.kiro` 为 `expired`），又看到恢复（`ok`），才自动继续——失败若不是登录造成的（登录一直正常），不会反复重跑。只适用于 Kiro 任务：其他工具的登录平台读不到。 |
| W3 | 自动继续 = 平台替用户续作失败的任务（该任务及其后未验收的任务重置），记变更 `run.resumed` 与原因；不计入、也不重置预算（不是用户的操作）。 |
| W4 | Worker 重新启用、执行环境重新服务该会话的空间、凭证重新可用：按会话所处的阶段继续（运行中的任务继续查看，准备中的重新准备）。 |

## 3．设计

### 3.1 健康检查（`Engine.probe`，独立线程每 60 秒调用）

- 选取：已启用、未退役的 Worker；其中有「等待 Kiro 登录」的会话的每次都查，其余距上次超过 10 分钟才查。
- `GET /health`（5 秒）：失败只记日志；成功且 `boundary` 与保存的一致 → 写回 `workers.config.capabilities`（含 `checked_at`）。
- 之后对等待 Kiro 登录的会话按 3.2 判断。

### 3.2 等待的条件与恢复（`waiting.py`）

| 条件 | 识别 | 满足 | 继续 |
|---|---|---|---|
| `kiro_login` | 会话 `blocked`，失败的 Attempt `failure_type: auth`，任务工具为 `kiro` | 失败后的健康检查先见 `expired`（Attempt 证据记 `waiting: {for: "kiro_login", expired_at}`），再见 `ok` | 失败任务及其后未验收的任务重置为 `pending`，会话 `ready` |
| `worker_enabled` | 会话 `blocked` 且 `error` 为「Worker 已停用」 | Worker 已启用 | 会话回到 `running`（任务仍在运行时）或 `ready` |
| `environment` | 会话 `waiting_worker`，已有 `worker_id` | `unserved()` 为空（重新启用、重新给到该空间） | 有原生父级 → `ready`，否则 `preparing`（与「分配 Worker」相同） |
| `credentials` | 会话 `blocked` 在准备阶段（无原生父级、无 Attempt），凭证不可用 | 凭证可用（重新启用、更换、授权恢复） | `preparing` |

- 每个 Engine 周期在 `recovery.reconcile` 之后调用 `waiting.resume(db)`（数据库判断，不发请求；`kiro_login` 的「见过过期 / 已恢复」由 3.1 写入）。
- 每次恢复记 `run.resumed`（原因：「Kiro 登录已恢复，自动继续」「执行环境已重新启用，自动继续」「执行环境已重新服务此空间，自动继续」「仓库凭证已可用，自动继续」）。

### 3.3 可见

- 会话 `attention`：可自动恢复的等待，标题与操作写明等的是什么、由谁处理、满足后自动继续：
  - 「等待 Kiro 登录恢复」——「请管理员执行 deploy.sh kiro-login；登录恢复后自动继续（平台每分钟检查一次）」；
  - 「执行环境已停用」——「管理员重新启用后自动继续」；
  - 「仓库凭证不可用」——原操作后加「；凭证可用后自动继续」。
- 时间线 `run.resumed` 的中文标签「条件满足，自动继续」。
- 执行环境列表的能力带 `checked_at`（「最近检查」）。

## 4．测试与验收

- **本机**：
  - 登录：过期 → 恢复后自动重跑并完成；登录一直正常时的认证失败不自动重跑；Claude 任务的认证失败不等待；
  - Worker：运行中停用 → 重新启用后继续查看并完成；准备中停用（`waiting_worker`）→ 重新启用后继续；
  - 凭证：停用致准备失败 → 重新启用后自动准备；
  - 健康检查：能力在边界不变时更新、变了不更新；Worker 不可达只记日志；
  - 自动继续不计入预算。
- **EC2**：运行中把 Worker 停用、几分钟后重新启用，会话自动继续并完成（不需要真的让 Kiro 登录过期）。

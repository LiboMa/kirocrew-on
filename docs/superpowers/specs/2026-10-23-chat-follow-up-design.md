# 在会话里继续和子 Agent 对话（D72，负责人 2026-10-23）

状态：设计稿，待负责人确认（2026-10-23）；确认前不实现。报告：`docs/reports/2026-10-23-dispatch-mechanisms.html`。

负责人原话：「如果客户想要继续从 Chat Session 与各个 Subagents 继续交互，现在的机制我们是否支持？如果没有请增加，
并阐释好其原理机制和细节，总结成 Docs，这个对我们技术来说，非常重要，一定要解释清楚。」

本文分三部分：先讲清 a183d84 之后父会话为什么不再逐个任务回复（§1），再说明现在能做到哪一步（§2），最后是要补上的机制（§3–§6）。
以 KiroCrew 0.10.0（EC2）为准；本机桌面版是 0.8.0，§2 注明差别。

## 1. 父会话为什么不再逐个任务回复

### 1.1 一个会话在 KiroCrew 里的样子

| 平台里 | KiroCrew 里 | 说明 |
|---|---|---|
| 会话 `run-<id>` | 父会话（chat slot）`octopus-run-<id>`，会话键 `dashboard:octopus-run-<id>` | Worker 在准备源码时建立（`worker.py` `prepare`），Agent 为 `poc-coordinator`，即「Owner 观察员」：只解释，不派发、不改源码 |
| 任务的一次尝试（Attempt） | 父会话下的一个子 Agent（`POST /api/spawn`，`parent_session` 为父会话键） | Agent 为 `poc-kiro` / `poc-claude` / `poc-codex`，诊断为 `poc-diagnose`；`keep: true`：子 Agent 的对话保留，可以续接 |
| 自动返工 | 在同一个子 Agent 对话上续接（`POST /api/spawn/{对话}/continue`） | D46 P5a：只在平台安排的返工、同工具同模型、对话没坏时 |

平台的 Engine 是唯一的派发者：它按任务表一个一个派、读结果、把关、纠错（见 `docs/reports/2026-10-23-dispatch-mechanisms.html`）。

### 1.2 KiroCrew 默认怎么处理子 Agent 的结束

子 Agent 结束时，KiroCrew 的 `_subagent_done`（`slack/gateway.py`）把一条「子 Agent 完成」的消息注入它的父会话：

1. 父会话空闲：立即为父会话跑一轮对话（`_run_chat`）——起一个 kiro 进程、消耗 Kiro credits，观察员读完结果写一段回复；
2. 父会话忙：排队，等这一轮结束再跑；
3. 一批子 Agent 的最后一个结束时，还会再排一轮「汇总」。

派发时的 `silent: true` 只关掉 Slack 和 Dashboard 的通知，不影响这一轮。平台既不读这段回复，也不需要它：结果平台自己从
`GET /api/spawn/{id}` 读。于是每个任务结束都白跑一轮模型，留下一个常驻到 TTL 的 kiro 进程（BACKLOG「子 Agent 结束时父会话仍跑一轮 coordinator」）。

### 1.3 a183d84 做了什么

KiroCrew 自己的阻塞式派发工具 `spawn_sub_agents` 有同样的问题：它已经把结果作为工具返回值交给了模型，不需要再注入一次。
它的办法是 `POST /api/spawn/mark-collected`（`dashboard/messaging_api/run_control.py`）：

```
POST /api/spawn/mark-collected
{"ids": ["<子 Agent ID>"], "parent_session": "dashboard:octopus-run-<id>"}
```

KiroCrew 把这些 ID 记进父会话的 `_subagents_inline_collected`（内存中的集合）。子 Agent 结束时，`_subagent_done` 在注入之前、
等待之后各查一次这个集合：在其中就记为已交付、直接返回，不注入、不跑这一轮，并取消汇总轮。

a183d84 让 Worker 在每次派发、续接与模型探测拿到原生 ID 后立刻调用它（`worker.py` `_quiet_parent`）。调用失败（旧 Gateway）不影响派发，
`dispatch.json` 的 `collected: true` 表示已标记。

### 1.4 现在父会话里看得到什么

| 内容 | a183d84 之前 | 之后 |
|---|---|---|
| 平台的建立说明（「Octopus MVP 1.0.0 已建立研发运行…」） | 有 | 有 |
| 每个 Attempt 结束时平台写的结果说明（「Octopus 执行 Attempt … 已返回。原生 Task … 实际后端 …」与结果摘要，最长 3800 字） | 有 | **有** |
| KiroCrew 注入的「子 Agent 完成」消息 | 有 | 无 |
| 观察员读完结果写的那一段回复 | 每个任务一段 | **无** |
| 最后的汇总回复 | 可能有 | 无 |

结果说明用的是 `POST /api/chat/slots/{slot}/note`：KiroCrew 在聊天记录里写一行可见的说明，同时把它放进下一轮的背景，
**不触发模型**（`dashboard/chat_handlers.py` `api_chat_slot_note`）。所以用户在聊天里仍能逐个看到每个任务的结果，只是不再有
观察员的「解读」；用户接着问，观察员能看到这些说明并回答。

EC2 核对（a183d84，run-d62631d5）：父会话记录 4 行——空行、建立说明、两条结果说明；Gateway 日志两次「skipping injection」、
零次 `_run_chat`。部署前同样两个任务的 run-656be0a4 跑了两次 `_run_chat`。

限制：集合只在 Gateway 内存中。任务运行中 Gateway 重启，这个任务结束时照旧跑一轮。

## 2. 现在能不能在聊天里继续和子 Agent 交互

| 想做的事 | KiroCrew 原生能力 | 平台现在 |
|---|---|---|
| 子 Agent 运行中插话 | 聊天里的 Agent 调 `spawn_steer` | 控制台「补充说明」/ `POST /v1/runs/<id>/steer`：只支持 Kiro 任务（0.10.0 只对 kiro 后端生效） |
| 子 Agent 结束后在它的对话上继续 | 聊天里的 Agent 调 `spawn_continue`（`keep: true` 的对话可以续） | 只有平台安排的自动返工续接原对话；用户的「续作」是新起子 Agent，不续接 |
| 界面上直接对某个子 Agent 发消息 | 没有：原生页面对子 Agent 只有列表、状态、停止、全部停止、对失败的「重试」 | 没有 |
| 在父会话聊天里让平台做 | — | 不支持：观察员被要求不派发，平台不读聊天 |

结论：**不支持**。

能绕过去吗：在原生页面用 `/agent` 把父会话的 Agent 换成会派发的 Agent，它可以对平台的子 Agent 调 `spawn_continue`。
但平台完全看不到——没有 Attempt、不跑检查与审查、不进时间线与用量；它在工作区里的改动会被下一个平台任务的候选提交带走，
还可能让下一个任务的「已验收的文件」检查报出不是它造成的提示。这条路不支持，也不建议。

本机桌面版 0.8.0 是同一套原生能力（`spawn_run` / `spawn_sub_agents` / `spawn_continue` / `spawn_steer`），只是没有 `mark-collected`
之外的平台把关；本机看不到 EC2 上的会话，因为两者是不同的 Gateway。

## 3. 要补上的机制：对话续接

### 3.1 原则

- **平台仍是唯一的派发者。** 聊天只是入口：每一次和子 Agent 的交互都是该任务的一次 Attempt，照常检查、记录、计入预算，
  在控制台的时间线与修订历史里看得到。
- **续接原对话。** 子 Agent 带着它上一轮的上下文继续（`/api/spawn/{对话}/continue`），而不是从头再来。
- **不加关卡。** 不加确认或等待；做不了时当场说明原因与可行的做法（负责人 2026-10-22：影响体验的关卡须先经同意）。

### 3.2 入口

| 入口 | 写法 |
|---|---|
| 原生父会话聊天 | `@<任务 ID> 内容`，例如 `@task-1 再补一段关于 checkpoint 的说明`（任务 ID 在每条结果说明与控制台任务卡片上） |
| 控制台 | 任务卡片上的「继续对话」 |
| API | `POST /v1/runs/<id>/tasks/<任务 ID>/follow-up`，`{"message": "…", "request_id": "…"}`，scope `execute` |
| MCP | `octopus_follow_up`（`run_id`、`task_id`、`message`） |

四个入口走同一个服务方法（`Service.follow_up`），行为与权限一致。

### 3.3 按任务所处的状态

| 任务状态 | 会话状态 | 做什么 |
|---|---|---|
| 运行中，Kiro | 运行中 | 转为补充说明（`steer`，`interrupt`），送入正在跑的这一轮 |
| 运行中，Claude Code / Codex | 运行中 | 不执行，说明「运行中的 Claude Code / Codex 任务不支持插话（KiroCrew 0.10.0），任务结束后再发」 |
| 已结束（已交接、失败、停止） | 已停下（完成、需要处理、失败、停止） | 对话续接（§3.4） |
| 已结束 | 正在执行别的任务 | 不执行，说明「会话正在执行 task-X，等它结束或先停止」 |
| 规划任务 `plan`、平台的 Knowledge 任务 | — | 不执行：改需求请用续作；Knowledge 由平台维护 |
| 还没有子 Agent 对话的任务 | — | 不执行：「这个任务还没有运行过」 |
| 已关闭、删除中的会话 | — | 不执行：先重新打开 |

### 3.4 对话续接的步骤

1. **登记**（一个事务）：
   - 会话版本加一，修订历史记一条「对话续接」（任务、内容、谁）；
   - 该任务与它之后的任务重置为待执行；
   - 纠错预算从此重新计算（与续作、同步相同）；
   - 会话回到待执行；
   - 审计 `task.follow_up`，时间线「对话续接：task-1」。
2. **派发**：Engine 照常为该任务新建 Attempt，发给 Worker 的派发里带：
   - `repair`：`{"follow_up": true, "message": "<用户内容>", "by": "<用户名>", "instruction": "本轮为用户在对话中的追加要求：在你上一轮的工作上按要求修改并重新验证；交接与结论写到本轮指定的文件。"}`；
   - `continue`：该任务最近一次子 Agent 对话。条件同自动返工：同工具、同模型、未单独指定 effort、上一轮对话没坏。与自动返工不同，
     用户此前的续作不妨碍这次续接，因为这正是用户要的。

   续不了（换过工具、对话出错、Worker 不支持续接）时新起子 Agent，它从指令里读到用户内容与上一轮的交接。
3. **执行**：子 Agent 在原对话里读到「这是同一任务的返工…」与本轮 `instructions.md` 里的「用户在对话中的追加要求」，在已有工作上修改。
4. **把关**：与任何 Attempt 相同——交接、结果文件、改动、秘密、检查命令；之后的任务按新结果重新执行，审查针对新的候选，
   并被告知原因（`repair.rerun`：「上游任务按用户在对话中的要求做了修改，本任务在新的源码上重新执行」）。
5. **回到聊天**：子 Agent 结束时，平台照常把它的结果说明写进父会话（§1.4）——用户在聊天里看到的就是这个子 Agent 的回复。

### 3.5 聊天入口如何工作

**平台怎么读到消息。** 平台平时不读父会话。对「8 小时内有人为它打开过原生入口」的会话（只有这种会话可能有人在聊天），
Engine 每 5 秒经 Worker 读一次父会话最近 20 条消息（Worker `/chat/inbox` → `GET /api/chat/slots/{slot}?limit=20`），
只看 `role` 为 `user`、晚于入口打开时间、以 `@任务 ID` 开头的消息；以（时间、内容）的摘要去重，已处理的不再处理。
其他消息照旧只由观察员回答。

**是谁发的。** 原生登录覆盖整个 Gateway（K03），消息本身不带身份。平台以「最近 8 小时内为该会话打开原生入口的人」为发送者，
按控制台同样的权限检查（§4）。这段时间里如果还有其他人打开过同一执行环境的原生入口，平台无法确定是谁发的：不执行，
在聊天里说明「多人持有这个执行环境的原生入口，无法确认是谁发的；请在控制台的任务卡片上继续对话」。

**回执。** 平台用 `note` 在聊天里写一行（可见、不触发模型）：
- 「已转交 task-1：在原对话上续接（第 3 次尝试）」，或「已作为补充说明送入 task-1 正在运行的这一轮」；
- 做不了时写原因与可行的做法。

**观察员。** 新会话的观察员背景里写明：`@任务` 开头的消息由平台转交，它只需一句话确认，不自行派发或续接。KiroCrew 对每条用户消息
都会让观察员回复一轮，这一轮由用户的消息触发，不是平台加的。

### 3.6 时序

```
用户（原生聊天）      KiroCrew 父会话          Engine / Worker                    子 Agent（task-1 的对话）
  │ @task-1 再补一段    │                          │                                   │
  │────────────────────►│ 记录 user 消息           │                                   │
  │                     │ 观察员回复一句（一轮）   │                                   │
  │                     │◄─────── 每 5 秒读最近消息 │                                   │
  │                     │                          │ 认定发送者、检查权限、登记续接     │
  │                     │◄─ note「已转交 task-1」──│                                   │
  │                     │                          │ 新 Attempt：/continue + 追加要求 ─►│ 在原上下文里修改
  │                     │                          │◄──────────── 结束（不注入父会话）──│
  │                     │                          │ 把关：交接、改动、秘密、检查命令   │
  │                     │◄─ note「Attempt 已返回…」│ 之后的任务重新执行                 │
  │ 在聊天里看到结果    │                          │                                   │
```

## 4. 权限与安全

- 谁能用：与续作、同步相同——能执行这个会话的人；D49 个人边界上只有边界的主人；Team 未归档；执行环境仍为这个空间服务。
- 内容 1–4000 字，不含控制字符；写入事件与修订前按 D57 打码（凭证、Worker Token）。
- 幂等：API / 控制台 / MCP 带 `request_id`；聊天消息以（会话、消息摘要）去重。
- 聊天发送者的认定见 §3.5；认定不了就不执行，不猜。

## 5. 成本

- 读取：只对 8 小时内打开过原生入口的会话，每 5 秒一次，一次最多 20 条消息。
- 不新增模型轮次：续接本身是用户要的那一轮；观察员对用户消息的回复是 KiroCrew 的原生行为。
- 之后的任务会重新执行（§3.4 第 4 步），与自动返工相同。

## 6. 我做的决定（可改）

1. **之后的任务重新执行。** 它们基于旧的输出，不重跑就可能带着过时的结论完成。代价：多跑几个任务。
2. **聊天发送者的认定规则（§3.5）。** 原生登录不分人，宁可不执行也不冒用身份。代价：多人共用一个执行环境时，聊天入口不可用，改用控制台。
3. **运行中的 Claude Code / Codex 任务不排队，直接说明。** 排队等于新增一种等待。代价：用户要等任务结束再发。
4. **观察员的说明只写进新会话。** 旧会话的 `@` 指令照样执行，只是观察员不知道这个约定。
5. **不接管用户在原生页面自己派出的子 Agent**（换过 `/agent` 之后的）。它们不经平台，仍不支持。

## 7. 测试与验收

- 服务：四种任务状态各自的结果；权限（非执行者 403、D49 非边界主人 403）；`plan` 与 Knowledge 任务拒绝；会话忙时拒绝；
  之后的任务重置；修订与审计；预算重新计算；幂等。
- Engine：带 `follow_up` 的 Attempt 发出 `repair.follow_up` 与 `continue`（用户续作过也续接）；续不了时新起子 Agent；之后的任务带 `repair.rerun`。
- Worker：`/chat/inbox` 只返回新的 `user` 消息；`/chat/note` 写 note；指令里有「用户在对话中的追加要求」。
- 聊天入口：只轮询 8 小时内打开过入口的会话；`@任务` 才处理；去重；多人持有入口时不执行并写说明；回执。
- 控制台：任务卡片「继续对话」；MCP `octopus_follow_up`。
- EC2：在 owner 边界上，一个会话完成后，在原生聊天里发 `@task-1 …` → 回执 → 原对话续接（`dispatch.json` 的 `continued`）→
  结果说明出现在聊天里 → 之后的任务重新执行；控制台任务卡片同样可用。

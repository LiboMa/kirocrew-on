# 原生入口改为单会话票据（K03 / M4-3）：现状与三种方案（待负责人选择）

日期：2026-10-26　·　起因：M4-3；调研时在 EC2 发现入口登录可延续 30 天，已先做过渡修复（PR #11）

## 1．现状

- **入口怎么工作**：会话页「在 KiroCrew 中打开」→ 平台核对是边界主人（R7）→ Worker 用本机密钥向 Gateway 要一个 token（`/api/token/local?ttl=1h`）→ 拼成 `<原生域名>/chat?sid=<父会话>&token=…` → 浏览器打开后，Gateway 把它换成登录 Cookie。
- **这个登录能做什么**：它是**整个 Gateway 的主人登录**，`sid` 只决定打开哪一页。登录的人能看、能停该边界上的所有原生会话。
- **能持续多久**：
  - 访问 Cookie 1 小时；
  - Gateway 另发一条 30 天的刷新凭据（2026-10-26 在 EC2 实测确认）。**过渡修复**（PR #11，已部署）：所有公网中转把刷新答成「已吊销」，登录在访问 Cookie 到期时结束。
- **平台收不回**：停用用户、取消共享，都碰不到 Gateway 里的登录；只能等它到期。
- **影响范围**：D49 以后入口只开放给边界主人，登录覆盖的是他自己的 Gateway，风险主要在「平台撤权后仍有至多 1 小时」与「共享环境的主人能看到别人的会话」（共享环境本就标明不分隔）。

KiroCrew 0.10.0 的 Gateway：

- **没有**按会话限定的登录；
- 有「不发刷新凭据」的声明（`no_refresh`），但 `/api/token/local` 设不了；
- 有吊销手段：吊销单个 Cookie（需要 Cookie 值，平台拿不到）、退出一条刷新链、`POST /api/logout`（本机密钥，结束该 Gateway 上的**全部**浏览器登录）。

## 2．三种方案

### 方案一 · 撤权即结束（平台侧，可马上做）

平台停用用户、取消其边界、或会话关闭时，让该边界的 Worker 调一次 `POST /api/logout`，结束这个 Gateway 上的全部浏览器登录。

- **好处**：不改 KiroCrew；撤权从「至多 1 小时」变成「立即」。一个边界只有一个主人，「全部登录」就是他自己的登录，不误伤别人。
- **不足**：登录仍覆盖整个 Gateway，不是单会话票据；共享环境（`personal`、`w1`）上会把主人的其他浏览器登录也一起结束。

### 方案二 · 请 KiroCrew 提供按会话限定的登录（根本解决）

请 KiroCrew 在 `/api/token/local` 上支持两个参数：

- `slot=<父会话>`：token 带上 slot 声明，换成 Cookie 时保留；Gateway 只放行这个 slot 的接口与实时事件，用它现有的「应用 token」路径白名单和按 slot 过滤的事件机制实现。
- `no_refresh=1`：不发刷新凭据。

另需一个本机密钥保护的「按 slot 或 nonce 吊销」接口。平台侧：Worker 传 slot、记下 nonce；撤权、关闭会话时调吊销。

- **好处**：真正的单会话票据；撤权立即生效；不需要我们维护代理规则。
- **不足**：取决于 KiroCrew 的排期；原生页面里访问全局接口（会话列表等）的地方要能处理 403。

### 方案三 · 平台票据 + 过滤代理（不改 KiroCrew）

平台给每个人、每个会话签自己的短期票据 Cookie。公网中转对每个请求和 WebSocket 升级都向平台核对（nginx `auth_request`），去掉浏览器带来的 Gateway Cookie，换上 Worker 签发的短期 Gateway 凭据。只放行页面资源和 `/api/chat/slots/<父会话>/*`，拦下会话列表、派生、配置与 `/api/auth/*`。

- **好处**：不等 KiroCrew，撤权立即生效。
- **不足**：
  - Gateway 的实时事件流（`/api/ws`）会把**所有**会话的事件推给主人登录。要么逐帧过滤，要么拦下 WebSocket，后者会让页面失去实时更新。
  - 放行清单要跟着 KiroCrew 每个版本调整，容易漏或误拦。

## 3．对比

| | 方案一 · 撤权即结束 | 方案二 · KiroCrew 单会话登录 | 方案三 · 平台票据 + 过滤代理 |
|---|---|---|---|
| 是单会话票据吗 | 否 | 是 | 是（靠代理） |
| 撤权何时生效 | 立即 | 立即 | 立即 |
| 要改 KiroCrew 吗 | 不要 | 要 | 不要 |
| 我们的改动量 | 小 | 小（Worker 传参、吊销） | 大（代理、票据、事件过滤） |
| 长期维护 | 无 | 无 | 每个 KiroCrew 版本核对放行清单 |
| 主要风险 | 共享环境上会结束主人的其他登录 | 排期 | 实时事件流泄露或被拦 |

## 4．我的建议

**先做方案一，同时向 KiroCrew 提方案二。**

- 方案一改动小、马上能做，让「撤权立即生效」成立；共享环境本就要退役（D49 第 3 期），误伤范围会越来越小。
- 方案二是根本解决，而且符合「以 KiroCrew 为基线、通过接口复用它的能力」的方向；需要 KiroCrew 支持的只是两个参数和一个吊销接口。
- 方案三维护成本高，WebSocket 的问题没有好的解法，不建议。

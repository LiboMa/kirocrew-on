## 1. 模型

| 方式 | 在哪 | 谁干活 | 平台做什么 |
|---|---|---|---|
| 自由对话 | KiroCrew 原生聊天（会话的父会话 `octopus-run-<id>`） | 主会话 Agent：回答问题，会话停下时也可以动手（派子 Agent 改代码） | 告诉它现在能不能动手；记下它派了谁 |
| 结构化迭代 | 平台控制台 / CLI / MCP 的「续作」 | 平台 Engine 按任务派发 | 把关、纠错、记录、发布 |

两种方式读写**同一份状态**：
- **工作区**：会话分支上的候选提交，加上尚未提交的改动；
- **平台记录**：任务、每次尝试的结论、交接、修订历史；
- **对话记录**：父会话的聊天，包括平台写进去的每条结果说明，以及聊天里派出的子 Agent 的结果。

两种方式之间切换时，做一次**状态归纳**。

## 2. 三条规则

1. **同一时间只有一个写者。** 平台在跑任务时，聊天里的 Agent 只回答问题、不动手；会话停下后（完成、需要处理、停止），
   聊天里的 Agent 可以直接动手。平台在会话每次开始运行或停下时，往聊天里写一行说明（`note`，不触发模型），告诉 Agent 现在能不能动手。
2. **聊天里做的事都留痕。**
   - 聊天里的 Agent 派的子 Agent 挂在本会话的父会话下，平台能列出来（`GET /api/spawn` 里 `parent` 是本会话、任务里没有平台的 Attempt 标记）；
   - 改动落在会话的工作区；
   - 这些子 Agent 结束时照常回到聊天，平台只标记自己派的。
3. **平台只在用户要求时接手。** 用户在 Web 端续作时，平台先做「对话 → 平台」的归纳（§3.2），再继续派发，聊天里的改动不会被覆盖或漏掉。

## 3. 两个归纳

### 3.1 平台 → 对话：用户进入聊天时

- 打开原生入口，或会话停下时，平台写一条「当前状态」说明。内容是：已完成的任务与结论、当前候选提交、下一步、上次为什么停下。
- 说明是确定性的，由平台记录生成，不跑模型。
- 每个任务的结果说明本来就在聊天里。所以**不需要恢复「每个任务的观察员回复」**：用户问的时候，Agent 从这些历史里找。

### 3.2 对话 → 平台：用户回到续作时

1. **平台核对事实**（不靠模型）：
   - 工作区相对上次候选提交改了哪些文件（git）；
   - 聊天里派过哪些子 Agent，各自的结果；
   - 这段时间的对话记录。
2. **请聊天 Agent 写结构化总结**，写到会话目录下的一个文件里：
   - 用户要了什么、做了什么；
   - 做了哪些决定；
   - 还没做完什么；
   - 需求有没有变。
3. **平台记为一次「对话中的工作」**，与 D58「本地同步」同一套做法：
   - 把工作区的改动提交成新的候选，照常做秘密检查、跑检查命令，命中只记提示；
   - 修订历史记一条，附上总结和事实清单；
   - 总结里的「需求变化」预填到续作的需求里，由用户确认。
4. **之后的任务以这个状态为起点。** 它们拿到的是平台核对的事实（改动、交接）；对话总结只作说明，避免总结里的错误被当作事实带下去。

## 5. 先验证：有效性与可行性

不改平台代码，在一个测试会话上做四个实验。

| 实验 | 做什么 | 看什么 |
|---|---|---|
| E1 上下文 | 会话完成后，在原生聊天里问「做到哪了、改了什么、为什么这样做」 | Agent 只凭聊天里的结果说明和交接，答得准不准 |
| E2 对话里动手 | 只在这个测试会话里放开「不派发」：让 Agent 派一个 `poc-claude` 子 Agent 改一个文件 | 改动是否落在工作区；子 Agent 是否挂在父会话下、平台能否认出它不是自己派的 |
| E3 归纳 | 让 Agent 写结构化总结，与 git diff、子 Agent 列表逐项对照 | 漏了什么、写错了什么 |
| E4 继续 | 以总结为输入续作，例如重跑 Evaluator | 后续任务能否在对话之后的状态上正确工作 |

记录三项：总结与事实的吻合程度、额外的 Kiro / Claude 轮次、每步耗时。

已查清的：
- 主会话 Agent（`poc-coordinator`）本来就带 KiroCrew 的派发工具，允许派的 Agent 已包括 `poc-claude` / `poc-codex` / `poc-kiro`
  （`composition/templates.py`）。目前拦住它的只是提示里的「不派发」。
- KiroCrew 派子 Agent 时可以指定工作目录；会话的工作区路径已经写在父会话的第一条说明里。
- KiroCrew 有 `POST /api/chat/slots/{slot}/project`，可以设聊天的项目目录。但改项目会重置对话历史，只能在建会话时设；
  `/workspace` 设的是 KiroCrew 的命名工作区，不是任意目录。

待验证的：
- 主会话 Agent 自己改文件时在哪个目录；
- 放开派发之后，与平台的派发白名单、被排除的工具是否冲突；
- 对话记录很长时，读取与归纳的成本。

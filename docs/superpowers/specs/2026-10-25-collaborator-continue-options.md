# 协作者怎样续作共享来的会话：三种方案（待负责人选择）

日期：2026-10-25　·　起因：负责人问「协作者是否要以某种方式续作这个会话，否则共享意义也不太大」

## 1．现在卡在哪

- **共享已上线**（D64，M4-1）：会话可以共享给某个人、某个 Team 或全公司，角色分「查看」和「协作」。
- **执行的位置**：自 D49 起每人有自己的执行环境，个人会话默认就在**创建者自己的执行环境**上跑。在那里，Agent 以创建者的身份运行：用创建者的系统用户、Kiro 登录、KiroCrew 记忆和仓库凭证，用量也算在创建者头上。
- **规则 R10**：在某人自己的执行环境上，只有这个人能下达指令，包括续作、诊断、确认计划、补充说明、答复批准请求。
- **结果**：协作者对这类会话只能查看、停止、关闭、发布，**续作不了**。对 Team 会话，Team owner 可以把等待中的会话改派到 Team 的公共环境；但已经停下的会话不改派，个人会话完全没有办法交出去。

R10 是故意这样设计的：让别人在创建者的环境上下指令，等于借用创建者的身份和凭证。所以要让协作者续作，问题在于**用谁的身份、在哪里续作**。

## 2．三种方案

### 方案一 · 接手到自己的执行环境（同一个会话）

协作者在会话页点「续作」时，平台问一次：「这个会话在 alice 的执行环境上。接手到你自己的执行环境继续？」确认后：

- **搬代码**：平台让创建者的 Worker 把会话分支连同完整历史打成 git bundle（D58 `pull` 已有这个能力），在协作者自己的执行环境里展开成同一个工作区。提交 ID 不变，所以已验收的任务、候选、修订历史都照旧对得上。
- **换执行人**：这个会话的「执行人」变成协作者。之后的任务以协作者的身份运行，用协作者的凭证和 Kiro 账号，用量也算在协作者头上。
- **还是同一个会话**：需求、计划、任务、修订、时间线都留在原处。时间线上记一条「bob 接手了会话（来自 alice 的执行环境）」。
- **可以接回**：创建者想接回来时，同样再搬一次。同一时间只有一个执行人，不会两边同时改。

**代价**：
- 创建者那边 KiroCrew 原生聊天的上下文、记忆不会跟过去，接手后从平台记录的最新状态继续。这和「从 Web 续作」的现有做法一致。
- 私有仓库要发布时，用的是协作者自己的仓库凭证；协作者没有写权限，就只能在平台上续作，不能发布。

### 方案二 · 创建者授权代为续作（委托）

共享时多一个勾选：「允许 bob 在我的执行环境上续作（以我的身份运行、用量算我）」。勾上以后，R10 对这个人放开，会话不动，还在创建者的环境上跑。

- **好处**：改动最小；KiroCrew 原生聊天和记忆完全连续。
- **风险**：协作者可以借 Agent 用到创建者的一切：创建者的仓库凭证能访问的所有仓库、Kiro 账号、记忆。比如他可以让 Agent 去读创建者的其他私有仓库。这放宽了安全底线，只能做成创建者明确勾选的「委托」，并且每次都要写审计。

### 方案三 · 复制一份到自己的执行环境（分叉）

协作者点「复制到我的环境」，得到一个**新会话**：代码搬法和方案一相同，需求、计划、已完成的任务都带过去，之后各做各的。

- **好处**：互不干扰，身份最干净；也适合「我想在你的基础上试另一条路」。
- **代价**：成了两个会话，原会话后面的进展不会自动同步。要合并回去，得靠仓库层面的分支和 PR。

## 3．对比

| | 方案一 · 接手 | 方案二 · 委托 | 方案三 · 分叉 |
|---|---|---|---|
| 续作后还是同一个会话吗 | 是 | 是 | 否，变成一个新会话 |
| 以谁的身份运行 | 协作者 | 创建者 | 协作者 |
| 凭证与用量 | 协作者的 | 创建者的 | 协作者的 |
| KiroCrew 原生聊天与记忆 | 不跟过去，从平台记录继续 | 完全连续 | 不跟过去 |
| 安全底线 | 不变 | **放宽**：协作者能借 Agent 用到创建者的凭证 | 不变 |
| 创建者要不要操作 | 不用：共享时选「协作」就够了 | 共享时要额外勾选委托 | 不用 |
| 同时有两个人在改吗 | 不会，同一时间只有一个执行人 | 不会 | 会，各改各的 |
| 改动量 | 中：搬工作区、换执行人、接回 | 小：放开 R10、加授权字段与审计 | 中：与方案一相同的搬法，再加复制会话 |

## 4．我的建议

**选方案一 · 接手。** 理由：

- 协作者真正能接着做，而且做的还是同一个会话，共享这件事因此有了实际用处；
- 身份、凭证和用量都归实际操作的人，安全底线不变，责任也清楚；
- 搬代码用的是 D58 已有的 bundle 能力，不用新造传输方式。

方案三可以作为方案一的补充，以后要用时再加，比如「复制到我的环境」。方案二只建议在你确实需要「完全连续的原生聊天」时再做，而且必须由创建者明确勾选委托。

## 5．选定后需要一起定的细节

1. **接手时的确认**：方案一里，协作者第一次续作会弹一次确认，因为这一步会把会话搬到他的执行环境。这是新增的确认步骤，需要你同意。
2. **创建者要不要被通知**：建议在会话的时间线上记一条，再给创建者一个站内提示，不做审批。
3. **Team 会话**：Team 会话在 Team 的公共环境上时，成员本来就能续作，不受影响；只有在某个人自己的执行环境上时，才走「接手」。

接手共享来的会话：技术设计（D74）

日期：2026-10-25　·　负责人选定方案一「接手」（docs/superpowers/specs/2026-10-25-collaborator-continue-options.md）

1．要做到什么

协作者或 Team 成员遇到一个跑在别人个人执行环境上的会话，现在做不了任何下达指令的操作（R10）。接手要做到以下几点：

  • 同一个会话：协作者能把同一个会话搬到自己的执行环境，然后以自己的身份续作。
  • 身份、凭证、用量归接手人：搬过去以后，以接手人的系统用户、Kiro 登录、仓库凭证运行，用量和并发额度也算在接手人头上。
  • 历史原样保留：提交 ID 不变，已验收的任务、候选、审查绑定、修订历史、时间线都照旧对得上。
  • 可以接回：创建者想接回时用同一个命令，把会话搬回自己的执行环境。

不做：

  • 不搬 KiroCrew 原生聊天的上下文和记忆；接手后从平台记录的最新状态继续。
  • 不搬被 .gitignore 忽略的文件（如 node_modules、.env、构建产物），新环境里的检查命令会重新生成它们。
  • 不复制会话（方案三），也不委托（方案二）。

2．概念：执行人

  • 字段：新增 runs.executor_id（迁移 14），空值表示与 owner_id 相同。
  • 两个角色分开：
    • owner_id（创建者）保留：归属、删除权、列表里「我的」。
    • executor_id（执行人）表示：会话现在在谁的执行环境上、以谁的身份跑。
  • 改为看执行人的地方：
地方现在看改为看
执行环境是否还服务这个会话（unserved、等待执行环境的自动恢复、同步、诊断、D73 收集）创建者的空间执行人的空间
并发额度（D61）创建者执行人
知识的空间（个人会话）创建者执行人（Team 会话仍按 Team）
仓库凭证创建者固定的凭证接手时改绑为执行人可用的凭证；没有可用的就记为「已移除」，此后不能发布
发布、补充说明、答复审批（may_publish）创建者、Team owner、管理员加上执行人
原生 KiroCrew 入口边界主人（R7），共享来的人永远不行执行人在自己的边界上可以打开
自动发布的执行身份创建者执行人

R10 不用改：它按会话所在环境的主人判断，接手后主人就是执行人，自然只有执行人能下达指令。创建者想再操作就「接回」。

3．谁能接手、什么时候能接手

POST /v1/runs/<id>/takeover {request_id, expected_version}：

  • 谁：能续作这个会话的人（创建者、Team 成员、协作身份的共享对象），并且会话现在在别人的个人执行环境上（directs() 返回原因）。查看身份的人不行；管理员不因管理员身份获得接手权。
  • 搬到哪：操作者自己唯一的专属执行环境（own(w, actor)，与 D49 R2 的放置规则一致）。没有就 409 no_own_environment，提示联系管理员开通。
  • 什么时候：
    • 会话没关闭，且处于停下的状态（SETTLED）；
    • 没有进行中的尝试、诊断、检查，也没有正在进行的接手；
    • expected_version 等于当前版本，否则 409 version_conflict。
  • 幂等：同一个 request_id 只接手一次，做法与续作相同。

命令本身只登记接手（snapshot.takeover = {state: "moving", to, by, from, requested_at}）并返回 202。真正的搬迁由引擎在后台完成，因为大仓库的传输可能超过请求超时。接手进行期间，续作、诊断、同步、改派、开关预览一律返回 409 takeover_in_progress。

4．搬迁：引擎在后台做的事

#在哪做什么失败时
1平台停掉旧环境上的远程预览继续（旧进程会被定时清理）
2旧 Worker有聊天里没提交的改动（D73 pending）时，先提交成「对话中的改动」：只提交、不跑检查，检查留到新环境再补；没有候选时以基线为父提交有疑似凭证（chat_secret）时，接手失败，说明原因并请创建者处理
3旧 Worker/pull/bundle（D58）打出会话分支的完整历史 bundle，上限 100 MB，同样做凭证检查超过大小或有疑似凭证时，接手失败，说明原因
4旧 Worker新增 /pull/attempts：把各尝试里下游会读的文件（handoff.md、outcome.json、decision.json、instructions.md）打成 tar.gz，上限 20 MB同上
5新 Worker新增 /adopt：bundle 与 tar 用原始字节发送，参数放在请求头。校验 bundle（只能有一个 head，即 refs/heads/octopus/<rid>，基线是它的祖先）→ 克隆到 workspace/project 并检出分支 → git 来源把 origin 设成源地址、禁止推送 → 原样写入平台给的 project.json（kind、source、requested_ref、基线 commit、branch）→ 展开尝试文件 → 写知识标记（按执行人的空间）与初始的 untracked-seen.json → 建 KiroCrew slot 与 parent.json（同 /prepare）→ 返回新的工作区路径和 slot 名引擎重试 3 次，之后接手失败；旧环境原样不动
6平台（一个事务）写入 worker_id、workspace、native_parent、executor_id；把各尝试证据里的 handoff_path 改写为新路径；凭证改绑；snapshot.placement = {kind: "taken_over", from, by}；清除 snapshot.takeover；版本加 1；记修订 taken_over 与事件 run.taken_over—
  • 失败时的处理：snapshot.takeover 改为 {state: "failed", reason}，记事件 run.takeover_failed，会话仍在原环境上、状态不变；控制台显示原因，可以再次接手。
  • 旧环境：不删除工作区，也不关闭原生会话，留给创建者自己查看。之后再做清理策略，见第 8 节。

5．接回

就是创建者自己对这个会话执行「接手」：会话这时在执行人的环境上，R10 拦住了创建者，directs() 返回原因，同一套流程把会话搬回创建者的环境，执行人变回创建者。

6．控制台、MCP、文档

  • 权限：run_permissions 增加 takeover（布尔）和 takeover_reason（为什么不能接手）。
  • 会话页：
    • 被 R10 拦住、takeover 为真时，「续作」旁边出现「接手到我的执行环境」。
    • 点开是一个确认对话框，写清：会搬到你的执行环境；之后以你的身份、凭证和用量运行；创建者可以接回；原生聊天的上下文不跟过去。有聊天里没提交的改动时，列出文件名，说明会先提交（同 D73 的提醒）。
    • 负责人在选方案一时已同意这一步确认。
  • 进行中：会话页顶部显示「正在接手到你的执行环境…」；失败时显示原因和「再试一次」。
  • 时间线与通知：时间线记「bob 接手了会话（来自 alice 的执行环境）」；创建者的会话列表里，这个会话标「已由 bob 接手」。
  • MCP：
    • octopus_status 的 access 与权限里带上 takeover；
    • 新增 octopus_takeover（第 2 期）；
    • Skill 写明：被 R10 拦住时，可以接手。
  • 文档：OPERATIONS 增加「接手共享来的会话」一节；D64 的共享说明里，协作者那一条补上接手；/v1/openapi.json。

7．测试

  • 单元测试与服务测试：
    • 谁能接手：协作者能；查看者不能；会话在自己环境上时不能；没有自己的环境时 409。
    • 状态与版本的前置条件、幂等、接手进行中时其他命令返回 409。
    • 执行人生效的地方：unserved、额度、知识空间、may_publish、原生入口、自动发布的身份。
    • 搬迁事务：handoff_path 改写、凭证改绑、修订与事件；失败时保持原状。
    • 接回。
  • Worker 测试：
    • /adopt 对 git、new、none 三种来源：提交 ID 不变，候选可检出，基线是祖先，project.json 原样；
    • 拒绝多个 head、拒绝基线不是祖先的 bundle；
    • 尝试文件展开后，handoff.md 可读。
  • 端到端（本机两个 Worker）：A 的会话完成两个任务后共享给 B；B 接手后续作第三个任务，任务在 B 的 Worker 上执行，审查绑定到 A 时的候选；A 再接回。
  • EC2 实测：用两个人的边界做一次真实接手。需要第二个账号，或者负责人指定的成员账号。

9．设计者决定（负责人可以改）

  1. 执行人可以发布、补充说明、答复审批。会话以他的身份和凭证在跑，这些都是续作时会用到的。
  2. 接手不需要创建者同意。共享时给了「协作」，就代表允许对方接着做；创建者能在时间线看到，也随时可以接回。
  3. 旧环境上的工作区留着不删：它在创建者自己的环境上，是创建者的东西。

10．实现时的取舍（2026-10-26）

  1. 谁来搬：搬迁不放进引擎的推进循环（它只推进进行中的会话），而由接手请求自己起一个后台线程完成；服务每分钟再检查一次，接着做被重启打断的接手。同一个会话同时只搬一次。
  2. 接手期间也不能停止、关闭、删除：会话本来就停着，拦下这些命令可以避免搬到一半时原环境被关闭。
  3. 尝试文件：除第 4 节列的四个文件，也带上 context.json；经平台按凭证规则遮蔽后再交给新边界（D57 §3.3）。新 Worker 只接受 attempts/attempt-<32 位>/ 下的这五种文件和一个 session.bundle，其他一律拒绝（409 adopt_invalid）。
  4. 项目记录：由原 Worker 随尝试文件给出（kind、基线、分支），平台核对来源与会话记录一致后交给新 Worker；不一致就不接手。
  5. 对话中的改动：提交后记为任务的一个尝试（checks_pass 记为跳过：「接手前提交，没有运行检查」），其后已验收的任务按 D73 重置为待执行。.env 这类文件不会被提交，留在原环境。
  6. 执行人也能更换凭证：凭证被记为「已撤下」时，执行人要能换上自己的凭证才能发布。
  7. 接回时的旧目录：原边界上旧的工作区目录改名为 <run>.before-<时间>-<随机> 留存，不覆盖。
  8. 再核对（终审 2026-10-26）：搬迁开始时与落地的事务里都再核对一次接手资格——共享被取消、离开 Team、目标环境已不是接手人自己的，就不接手（takeover_forbidden）。接手期间引擎不恢复、不核对这个会话；落地时会话若已在原环境又开始执行或已关闭，也不接手（takeover_conflict），停下后可以再接手。
  9. 遮蔽：尝试文件除凭证规则外，也遮蔽平台调用原 Worker 的 Token。
  10. 改派与执行人：等待执行环境的会话被分配到操作者自己的边界时，执行人改为操作者（在自己的边界上跑就以自己的身份）；其他改派按执行人的空间判断。
  11. 留到第 2 期：接手前提交的「对话中的改动」不加版本、在新环境也不补跑检查（只在提示里写明）；失败时它仍留在会话里（原环境的提交是真的）。
  12. MCP 提前到第 1 期（2026-10-26）：octopus_takeover 与 octopus_status 的 permissions / executed_by / takeover。Skill 要求调用前先征得用户同意，等同于控制台的确认框。
  13. 按人的用量提前到第 1 期（2026-10-26）：不在各处创建尝试时打标签，而是按时间线里 executor_id 的变更推出每个尝试创建时的执行人；对所有创建路径与历史尝试都成立。会话经手不止一人时，视图的 usage.by 按人列出。

# 发布：新建源码的会话发布到新仓库（D48）

## 1．背景

EC2 `run-f7670bfb…`（负责人 2026-10-17）：需求是「在 https://github.com/LiboMa 下新建一个 Repo，之后推一个 README 来完成 Repo 创建的测试」，
会话以新建源码启动。Agent 没有仓库写凭证（设计如此），平台的「发布到仓库」只能发布到会话启动时的仓库（`source.type = git`），
因此这个需求目前无法完成。负责人同意支持：**发布时新建仓库**。

不变的前提：Agent 依然没有任何凭证；创建仓库与推送都由平台以发布者的凭证完成，并经过与现有发布相同的核对（D35 §5.2、D37 §7、D47）。

## 2．已确定（负责人 2026-10-17 审阅通过）

| 编号 | 决定 |
|---|---|
| R1 | 只用于源码不来自远端仓库的会话（`source.type = new`）。发布请求带 `repository: {owner, name, private?}`（`private` 默认 true）；托管方取自所选凭证（github.com、GitHub Enterprise Server、GitLab）。 |
| R2 | 凭证要求：写权限，`repos` 范围覆盖 `owner/name`（如 `LiboMa/*`），并能创建仓库（GitHub classic PAT 的 `repo`，或细粒度令牌对账户的 Administration 写权限；GitLab 的 `api`）。缺权限时如实说明需要哪一项。 |
| R3 | 创建：GitHub 在 `owner` 是凭证本人时调 `POST /user/repos`，否则 `POST /orgs/{owner}/repos`；GitLab 在 `owner` 命名空间下 `POST /projects`。不自动初始化（无 README / license）。 |
| R4 | 推送方式：会话的基线提交推到新仓库的默认分支 `main`（新仓库为空，没有可覆盖的内容），会话的工作推到 `octopus/<run>` 并建 Draft PR 指向 `main`——与已有仓库的发布一致，合并仍由人决定（负责人选定；不采用工作直接进 `main`）。 |
| R5 | 同名仓库已存在时：若为空仓库（没有任何分支）且凭证可写，按 R4 发布到它（用户可以先自己建好空仓库）；否则拒绝并说明「仓库已存在且不为空」，不推送。 |
| R6 | 新仓库只建一次：会话记录发布目标 `publish.repository = {host, path, url, created}`；之后再次发布（新的已验证候选）与已有仓库相同——快进推送 `octopus/<run>`，沿用 Draft PR。会话的 `source` 保持原样（记录会话从哪里开始）。 |
| R7 | 自动发布（D47）：启动时 `publish: {auto: true, repository: {...}}` 由用户明确给出时，完成后自动建仓库并发布。规划者从需求中识别到「新建仓库」时只记说明并在「需要处理」提示用户在会话页确认目标，**不自动创建**——创建仓库是对外的、难撤销的动作，由人给出名称。 |
| R8 | 审计：每次创建写 `credential.use`（`action: repo.create`，结果），时间线 `run.published` 附新仓库地址；创建成功但推送失败时如实记录，再次发布沿用该仓库。 |

## 3．可见

- 会话页（新建源码的会话）：发布区显示「发布到新仓库」——owner、仓库名、私有（默认勾选）、凭证；按钮「新建仓库并发布」。已建好后显示仓库链接与 Draft PR，按钮回到「再次发布到仓库」。
- 控制台向导：新建源码时可选「完成后发布到新仓库」并填写 owner / 仓库名（与「完成后自动发布」开关配合）。
- API / MCP：`POST /v1/runs/<id>/publish` 接受 `repository`；`octopus_start.publish.repository`；Skill 写明：用户明确给出仓库名时才传，否则完成后询问。
- 「需要处理」：推送失败的新建源码会话提示「在会话页填写新仓库并发布」（替代 d417ee2 的「下载源码」说明）。

## 4．安全底线

- 名称校验：owner / name 只接受托管方允许的字符（GitHub：`[A-Za-z0-9._-]`，name ≤ 100）；不接受路径分隔与 `..`。
- 与现有发布相同：写凭证不进入执行环境；只推已验证候选；秘密扫描覆盖全部历史；不 force push；只快进。
- 只在新建（或确认为空）的仓库上写默认分支；已有内容的仓库一律不碰默认分支。

## 5．测试与验收

- **本机**（假托管方 API 与本地裸仓库）：GitHub 用户 / 组织与 GitLab 的创建调用；基线到 `main`、工作到 `octopus/<run>`、Draft PR；同名空仓库发布、非空仓库拒绝；
  缺建仓库权限的说明；只建一次与再次发布；自动发布由用户给出目标时创建、规划者标注时只提示；名称校验；审计与时间线。
- **EC2**：在负责人同意的账户下新建一个私有测试仓库，会话完成后发布，核对仓库的 `main` 与 Draft PR；验收后由负责人决定是否删除该仓库（平台不删除仓库）。

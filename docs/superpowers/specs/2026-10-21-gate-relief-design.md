  - run-9dce9610（进度 Dashboard）：

## 2. 原则（负责人已定）

1. **安全底线彻底拦住**：不降级，规划者、协调者和 Agent 都不能绕过。
2. 除安全底线外，只在两种情况下拦：**结果不可信**（执行本身失败，或实际运行的不是指定的工具或模型），以及**用户在需求里明确要求的验收**没过。
3. 其余规则一律降级为**提示**：结果照常交付，提示写在会话页和报告里，由审查任务和用户判断。
4. 不做模式开关，所有会话都是同一套规则。

## 3. 安全底线（硬拦）

### 3.1 扫什么

现在只扫候选提交的 diff，以及发布时带出的历史中的 `.env`（`octopus/sources.py`）。扩充为以下全部：

- 候选提交，以及发布时的整段历史（现有）。
- 不入库但会交到人手里的文件：预览、下载，以及工作区根目录或合同声明的交付物（如补丁、预览 `index.html`）。在提供预览或下载链接前扫描；会话完成前也再扫一遍。
- 展示给人的文本：交接、结果、检查命令输出尾部、状态摘要（控制台、MCP、报告）。发现疑似密钥时**打码后展示**，并按 3.3 停下。
- 发布到外部仓库之前，用同一套规则复扫。

只扫会话产生或改动的内容：基线里原本就有的文件不扫（很多仓库自带示例 Key，全扫会让该仓库的每个会话都停下），发布时带出的历史除外。〔设计者决定〕

**打码落在哪一层**〔设计者决定〕：
- 平台自己保存的副本在**写入时**打码，包括 Attempt 的 result 与 evidence（检查输出尾部等）、journal、报告。展示层不再依赖临时打码。
- Worker 主机上执行边界内的原始文件（如 `handoff.md`）保留原样，作为证据，权限不变。
- 原生 KiroCrew 页面与 observe 的实时对话，平台控制不了，作为已知限制写进 OPERATIONS。

**完成后才扫到**：预览或下载前扫到疑似密钥时，拒绝给出链接。即使会话已经 completed，也改为安全阻塞，处理方式同 3.3。

### 3.2 认什么

在现有的 GitHub fine-grained / classic / OAuth / App Token、GitLab Token、AWS Access Key ID（`AKIA`）、私钥之外，增加：

- AWS 临时凭证 `ASIA…`，以及紧跟 `aws_secret_access_key` 的 40 位密钥；
- Anthropic、OpenAI 的 API Key；
- Slack Token；
- 平台自己签发的 API Token 与 Worker Token；
- `.env` 文件（现有）。

具体正则由实现者定，要求有用真假样本写成的测试。

### 3.3 命中后

1. 会话立即停下，状态记为安全阻塞，后续任务都不派发。不交给协调者诊断，也不自动重试。
2. 提示写明文件、行号和密钥种类；匹配内容只显示首尾几位，任何地方都不出现明文。
3. 负责人判断：
   - **真密钥**：让 Agent 删除并清理提交历史，同时提醒负责人吊销或轮换。处理后重新扫描，通过才继续。
   - **误报**：负责人标记「误报」，并写一句理由。
4. 只有会话创建者、Team owner 或管理员能做第 3 步的判断；Token 和 Agent 不能做。

**安全阻塞期间**〔设计者决定，为守住「不能绕过」〕：
- 续作、恢复、确认验收、发布都被拒绝，无论来自控制台、API 还是 MCP Token。
- 唯一可做的操作是第 3 步的判断，以及停止或关闭会话。

**判断后**：
- 判为「真密钥」：平台用原任务的工具派发一个固定的清理任务，内容是删除密钥并改写本会话分支的历史，不改基线；同时提醒负责人吊销或轮换。
- 判为「误报」：直接进入复扫。

复扫通过后，原任务从安全门禁之后继续，跑完剩下的门禁再判定，**不整个重跑**。复扫仍命中，就再次停下。

### 3.4 误报记忆

- 一条记忆 = 作用域 + 位置 + 匹配内容的哈希，外加谁、何时、理由。不保存明文。〔作用域与位置为设计者决定〕
  - 作用域：所在空间（个人或 Team）+ 仓库，与 Team 知识的隔离方式一致。新建项目没有仓库时，作用域为本会话。
  - 位置：文件为相对路径；交接、结果、检查输出等文本，位置为来源类别加任务（如「task-2 的检查输出」），所以同一任务每一轮输出的同一个样例 Key，只需确认一次。
- 只有人能添加，可查看、可撤销；添加和撤销都写审计。
- 只对**完全相同的那一处**生效：换了文件，或内容变了，照样停下重新判断。不支持通配。
- 作用域跟随仓库：同一仓库的后续会话都认这份记忆。

## 5. 检查命令（checks_pass）

1. **两类检查**：
   - **必过检查**：需求里用户明确写出的验收，如「pytest 全过」「--check 退出 0」，由规划者在计划中逐条标为必过，并注明对应需求原文的哪一条。
   - **建议检查**：其余检查，只出报告。
2. 规划者不再被要求每个 implement / test 任务至少写 1 条 verify（`octopus/planning.py:47`），改为可以给建议检查。
3. 用户在续作中可以把某条检查改为必过或建议（`octopus_continue` 的 `execution.verify` 一并带上标记）。
   **没有标记时按来源判断**〔设计者决定〕：
   - 人写的检查一律算必过：经 MCP、API 或控制台提交的 steps，保存的工作流，续作时改的 verify。
   - 规划者生成的检查：只有注明了对应需求原文的才算必过，其余算建议。
   - 上线时仍在运行的会话也按这条判断。
4. **环境原因不拦**：命令因执行环境失败时记 `warn`「无法执行（环境）」，不触发纠错，必过检查也一样。识别依据：退出码 127、`command not found`、`No module named`、`Committer identity unknown`，具体列表由实现者定，要有测试。提示里要请用户确认环境，或把这条检查改写成可执行的形式。
5. **检查环境与执行环境对齐**：检查运行器至少提供 git 提交者身份的默认值（如 `GIT_AUTHOR_NAME` / `GIT_COMMITTER_NAME` / `EMAIL`），让需要建提交的检查（`git am`、`git commit`）能跑。规划阶段把 `environment.commands` 告诉规划者（现有），继续保留。

## 6. 纠错规则

1. **replan 额度**：因环境或合同问题做的修正不占「每会话一次」的额度。例如：检查命令在环境中不可执行、计划里的约定与续作的新需求冲突。协调者用一个新动作，或在 replan 中标明原因，实现者自定。
2. **防空转**：同一任务、同一失败门禁，诊断连续 2 次给出 `wait_for_user` 后，不再自动派诊断员。〔以下细节为设计者决定〕
   - 用户在控制台或 MCP 点「恢复」时，直接展示上一次 `wait_for_user` 的原因与说明，不再诊断。
   - 提供一个次要操作「仍要重新诊断」，用户明确点了才派。
   - 计数在两种情况下清零：用户续作（改了需求或任务合同），或该任务通过。
3. **平台自身故障自动重试**：诊断任务（`poc-diagnose`）和普通任务一样，原生运行时退出、沙箱初始化失败、因内存不足排队超时，都自动重试，计入现有的自动重试预算（默认 4 次、720 分钟）。不直接把会话判为 blocked。
4. 保留不变：审查须用与作者不同的工具；用户指定的工具和模型不被替换（`requested`）；看门狗（30 分钟无进展、单次 170 分钟）；自动重试预算。

## 7. 配套修正（非门禁，但都是当天红线的来源）

1. **候选自动提交排除不入库的交付物**：合同 `deliverables` 中声明为「不提交」的文件，不进入平台自动提交的候选。当天 run-9dce9610 的 task-2-2 因此返工 3 次。
2. **内存不足要看得见**：spawn 回执带 `reason: low_memory`（Gateway 推迟启动）时，状态显示「等待主机内存」，不显示「原生任务归属当前不可核实」。控制台的执行环境页显示主机可用内存。
3. **/tmp 是内存盘**：EC2 上的 `/tmp` 是 tmpfs，Agent 遗留的下载曾占用 4.7 GB。Agent 的临时目录改到磁盘，或定期清理没人用、超过一段时间的目录（运维项，方式由实现者定）。
4. **有提示就不自动发布**：自动发布（D47）只在会话没有 ⚠ 时触发。有任何 ⚠（含必过检查「无法执行（环境）」、审查改动被撤回）时，等负责人确认后再发布。依据：负责人的规则是推送前须经主人确认。〔设计者决定〕

## 8. 提示文案

每个停下或提示的状态写清三件事：**发生了什么**、**是你的问题还是平台的问题**、**建议怎么做（一个首选按钮）**。不出现 `failure_type`、门禁英文名这类内部词，英文名放在详情里。示例：

- 现在：「协调者需要你处理具体阻塞 · 自动诊断未形成可执行决定：协调者执行失败或已停止」
- 改为：「诊断员启动失败（平台临时故障，已自动重试 1 次）。你的任务结果都在。[重新诊断] [查看结果]」
- 现在：「✗ diff_present · 任务没有改动任何文件」
- 改为：「⚠ 本任务没有改动入库文件。如果它本来就只产出补丁或报告，可以忽略。」

## 9. 不做什么

- 不做检验强度的开关或模式。
- 不降低安全底线；误报只能逐处人工确认，不提供批量或通配放行。
- 降级不等于通过：报告如实区分 ✓ 通过、⚠ 提示、✗ 失败，不把提示藏起来。
- 不改变「Engine 是唯一派发者」「审查独立」「用户指定的工具与模型优先」这些既有规则。

## 10. 验收

用当天的真实现场回放（单元或集成测试中构造等价状态）：

1. deliver 任务只产出不入库的补丁：任务 accepted，记 ⚠「没有改动入库文件」。
2. 实现任务改了已验收任务的文件（M0 情形）：任务 accepted，记 ⚠ 并列出文件；后续审查能看到。
3. 检查命令因 `pytest` 不存在或缺 git 身份失败：记 ⚠「无法执行（环境）」，不触发纠错；有了 git 身份默认值后，`git am` 检查能通过。
4. 规划者自己写的建议检查失败：记 ⚠；需求里明确写出的必过检查失败：任务 blocked，进入纠错。
5. 不入库的补丁里含疑似 Token：会话安全阻塞，提示打码；负责人标「误报」后，重新扫描通过；同一处第二次扫描不再停下；内容改变后再次停下。
6. 交接或检查输出里出现疑似密钥：展示内容已打码，会话安全阻塞。
7. 诊断员沙箱初始化失败：自动重试；连续 2 次 `wait_for_user` 后，手动「恢复」不再派诊断员。
8. 审查任务改了文件：文件被撤回，审查结论照常采用，记 ⚠。
9. 安全阻塞期间，用 MCP Token 续作或恢复被拒绝；负责人判为真密钥后，清理任务改写会话分支历史，复扫通过后原任务从剩余门禁继续。
10. 带 ⚠ 的会话完成后不自动发布；没有 ⚠ 的照常自动发布（如开启）。

## 13. 实现时补充的决定（2026-10-22，设计者决定）

1. **必过检查受保护**：重新规划与 `verify_fixes` 不能删除或改写必过检查；替换任务时，被替换任务的必过检查须由新任务原样承接，否则计划不合法。只有用户续作能改必过 / 建议。
2. 规划者标必过时引用的原文，须是需求原文的子串（规范空白后比对），否则按建议检查。
3. 检查命令改为**全部执行**，不在第一条失败时停下，免得建议检查失败挡住后面的必过检查。
4. 审查改动撤回后，审查结论照常采用，`evidence.reviewed` 记为候选，计入发布所需的审查。
5. 「人」的判断只接受控制台登录（Token 标签为 `Web login`）的会话创建者、Team owner 或管理员；API / MCP Token 一律拒绝。
6. 完成后才扫到（预览、下载、发布）：会话改为安全阻塞，关联最后一个产生候选的任务；判为真密钥时，清理任务派给该任务。
7. 复扫后「从剩余门禁继续」：同一 Attempt 用平台已保存的原生结果重新判定，不重新派发 Agent；清理任务是同一任务的新 Attempt，通过后按它的候选继续。
8. 防空转按「同一任务 + 同一失败门禁（无门禁时按 failure_type）」计数；「仍要重新诊断」= 手动恢复带 `rediagnose: true`。
9. 自动重试新增两类平台故障：沙箱初始化失败（`AcpSandboxInitFailed` / `sandbox failed to initialize`），以及准入队列因内存不足结束（`waiting for memory` / `never started`）。诊断任务同样适用；计入自动重试预算，不计纠错轮数。
10. 「不提交」的交付物：合同新增 `untracked` 字段（路径列表），规划者为补丁、预览页等声明；候选自动提交排除这些路径，交付时扫描它们。
